# F1: 子の質問を残したまま、窓口から親を立て直す

## 始める状態

使い捨ての非公開リポジトリに、完了の状態が「サポート担当が手順書で受付時刻を確認できる」の Epic と、手順書の時刻表記を更新する子 Task を作ります。Epic の本文に「時刻は日本時間で記載する」という合意済みの決定を書きます。子の本文には受付時刻と直すファイルを記載し、タイムゾーンは書きません。

窓口と親は別のセッションにします。親の端末と稼働状態を窓口から見分けられるよう、試行用の親は Orca のワーカーとして起動し、子を別の Run で管理できるようにします。親は子のための実際の Orca Run を作って ID を Epic に記録し、子の worktree にワーカーを起動します。作業に使う spec は通常の型を使います。子が手順書の日付・時刻を書く直前に、時刻の基準について子 Issue に全文をコメントし、`ask` するよう試行を準備します。

## 実行

1. 観測側で `orca orchestration inbox --terminal run:<Run ID> --full --json` を使い、子の質問コメントと `ask` が揃った時点を特定します。親が返答する前に、試行用の親のセッションだけを閉じます。閉じる先は `orca terminal list --json` で親の worktree に対応する端末を確認し、`orca terminal close --terminal <親のハンドル>` で指定します。子の worktree とセッション、Run は残します。先に親が答えた場合は、停止の条件を作れなかった試行として種からやり直します。
2. デフォルトブランチの窓口に「次は何をする？」とだけ送ります。Run id や未回答の質問の中身を別途教えません。
3. 窓口が立て直した親と、元の子の続きの処理を観測します。質問の返信、子の作業 Issue の報告と閉じ方、`worker_done` の着信を記録します。

## 正しい結果

窓口が同じ Epic に新しい親を 1 回だけ起動します。新しい親は、子 Issue のコメントにある質問を拾い、合意済みの日本時間で進めるよう答えます。元の子はその回答を受けて作業を続け、成功の `worker_done` を送ります。元の子と並行して同じ作業のワーカーを二重に起動した場合は不合格です。

## 通しの試行に共通する記録

F1〜F4 は、#88 に従って固定した短い版の AGENTS.md とスキルありの条件で、代役の `orca` や `gh` を使わずに実行します。#88 の評価基準に従い、既存の長い AGENTS.md・CLAUDE.md やメモリを引き継がないよう試行用エージェントを設定して、各ケースを Claude と Codex で各 3 回実行し、毎回未使用の Issue と worktree、およびケース固有の Run を用意します。試行用のリポジトリ、Issue・PR 番号、Run id、worktree の絶対パス、ワーカーの Dispatch id を評価者の記録に残します。入力用の README や Issue の本文には、採点の基準や他の試行の結果を書きません。

観測には `gh issue view --json body,comments,parent,subIssues,state,stateReason`、`gh pr view --json state,mergedAt`、`orca orchestration inbox --terminal run:<Run ID> --full --json`、`orca orchestration worker-list --run <Run ID> --json`、`orca worktree list --json` を、必要な範囲で使います。受信箱の観測には、既読にしない `inbox` を使います。利用者への返事と最終状態を保存し、コマンド列の一致ではなく各ケースの正しい結果を採点します。通信障害などで必要な開始状態を用意できなかった場合は、行動の失敗と区別して記録します。
