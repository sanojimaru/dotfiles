## Issue と作業の進め方

- 目標・Epic・作業の 3 層で進める。目標はマイルストーン Issue（複数の Epic にまたがる依頼で使い、成功の条件だけを持つ）。Epic は親 Issue（type: Feature。利用者が使える変化 1 つで、完了の状態は MVP まで。計画は案として持つ）。作業は子か単独の Issue（type: Task。4 時間で閉じる大きさで、1 時間に満たない見込みの作業は、依存関係の近い次のストーリーと束ねる。4 時間と 1 時間は仮の値）。計画を持つのは Epic だけで、作業の Issue は子を持たない。計画と進み具合は Epic と作業の Issue にだけ置く。
- 作業 Issue は、工程（調査・設計・実装・テスト）で割らず、ストーリーで割る。1 つの作業 Issue のセッションが、そのストーリーの調査・設計・実装・テストから PR のマージまでを通して行う。工程ごとに別の Issue やセッションに分けると、引き継ぎのたびに文脈が落ち、前の工程で下した判断の理由が後の工程に届かないから。エージェントやスキルの評価データセットを作る作業は、テストの工程ではなく、測定の道具を作る別のストーリーとして扱い、評価されるエージェントやスキルを作るセッションには見せない。作る側が見ると、評価データセットに合わせて作ってしまい、測った数字が別のデータでは再現しないから。
- 閉じた Issue に残りを置かない。閉じる前に、片付かなかったことを開いた Issue に移す。閉じた Issue のコメントは、次の着手のときに誰も読まないから。
- 課題は見つけた時点で、開いた Issue に置く。今の Epic の完了の状態に要るなら Epic の計画に入れてもらい、要らなければ backlog の Issue にする。会話や PR の本文にだけ残すと、セッションが終わったときに消えるから。
- backlog の Issue には、何が起きているか（起きうるか）・根拠・困る人だけを書き、解決策は書かない。分からないことは「未確認」と書く。拡張や対象外も、分かった時点で backlog にする。
- セッションに何かを送るときは、送る前に、同じ全文を下の層の Issue にコメントする（ワーカーと coordinator ならワーカーの作業 Issue、窓口と親なら Epic）。Orca の通知は相手を起こす合図で、中身の正本は Issue のコメントにする。セッションが落ちても、代わりのセッションが Issue から続けられるようにするため。
- 利用者が話すのは、窓口（デフォルトブランチのセッション）と Epic の親（coordinator）だけ。ワーカー（子・単独タスク）は利用者に話しかけない。利用者の判断が要ることや止まる依存は、作業 Issue にコメントしてから `ask` で coordinator に上げ、ターンを終える。指示書の本文を利用者に見せて OK をもらう、捨てる案を出す、合意を取る、のような利用者との確認が要る規則に当たったときも、同じ経路で coordinator に上げ、coordinator が利用者に聞く。
- ワーカーは、マージ → 作業 Issue に報告（片付いたこと・片付かなかったこと・計画に影響する発見）→ Issue を閉じる → `worker_done` の順で終える。worktree は `worker_done` を受けた coordinator が片付ける。`hold-merge` が作業 Issue か PR に付いていれば、マージせず、承認を求める内容を作業 Issue にコメントしてから `ask` で求める。
- 窓口は、次の着手を決める前に毎回、止まった作業を確かめる。対象は、親のセッションが止まった開いている Epic、coordinator が居なくなった単独タスク、報告のコメントが無い閉じた子、開いた Epic の無いマイルストーン Issue、`backlog` の全件。<!--skill-->確かめ方と、Issue の立て方・渡し方・閉じ方は、スキル `issue-planning` にある。次の着手を決める前と、依頼を Issue にする前に読む。親は、渡された指示に従い、スキルの入口にある「Epic の親が読む節」から場面に合った参照を読む。<!--/skill-->
