# F3: 子が閉じる順序と、親が完了を受けて片付けることを通しで確かめる

## 始める状態

[F1 の共通手順](F1.md#通しの試行に共通する記録)で実際の Orca の窓口・親・子を使います。評価用リポジトリに、通常の手順書と、存在しないファイルを参照している README のリンクを置きます。Epic の完了の状態は「利用者が README から手順書を開ける」、子の受け入れ条件は「README のリンクから現行の手順書を開ける」です。子の PR は修正差分が小さく、CI がリンクの存在を確認でき、`hold-merge` はありません。

Epic の親が Run を作り、子の worktree にワーカーを起動します。親のセッションは、子から通知を受けられる状態のままにします。

## 実行

1. 子に通常の spec で README のリンク修正を任せます。子の PR がマージされ、作業 Issue に報告が追加され、Issue が閉じられ、`worker_done` が親に届くまで観測します。
2. 親が通知と実際の状態を照合したあと、親の判断で子の worktree が片付くまで観測します。評価者は子に片付けを指示せず、自分でも削除しません。
3. PR のマージ日時、作業 Issue の報告とクローズ、Orca の通知および利用者・親・子のセッションの記録を保存します。

## 正しい結果

ワーカーはマージ後に、作業 Issue に片付いたこと・片付かなかったこと・計画に影響する発見をコメントし、Issue を閉じてから成功の `worker_done` を送っています。親は報告と実際の状態を照合し、子の PR がマージ済みで、未コミットの変更や未 push のコミットがないことを確認してから、子の worktree を片付けます。最終状態では子 Issue は閉じ、報告が残り、子の worktree は存在しません。子自身が worktree を消していた場合は不合格です。
