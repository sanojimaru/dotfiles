# S3: Epic の計画を書く

親が、利用者が使える最小の変化を定め、子の作業を始められる計画にする。

渡された Epic の本文には、困りごとと確認した事実だけがある。目的・完了の状態・計画は、親が調べてから書く。調べる前に書くと、計画が浅くなる。

## 手順

1. Epic の本文を読み、リポジトリのファイルと既存の Issue を調べる。
2. Orca の Run を作り、返ってきた Run の id を Epic の本文に「Run id: `<id>`」の形で書く。落ちた親を立て直すとき、新しい親がこの id で Run を再開する。

   ```sh
   orca orchestration run-create --objective "<Epic の目的>" --json
   ```

3. Epic の本文を、`gh issue edit <番号> --body-file <ファイル>` で次の形に書き換える。コメントに書くだけでは、子と次の親が本文から読めない。元の困りごとと事実は残す。
   - 完了の状態: MVP（その変化が使える最小の形）まで。「〜として〜できる」のストーリーごとに、観測できる確認項目を置く。完了の状態は固定で、後から狭める方向にだけ直す。
   - 利用者の流れ: 利用者の操作や画面の順を、Mermaid の flowchart で書く。
   - 計画（案）: 子の作業の依存グラフを Mermaid で書く。最初の子は、利用者の流れを 1 本だけ、最も短い形で、必要な層すべてに通すものにする。計画は案で、分かったことで書き換える。
   - 外したもの: 拡張と「対象外」は、backlog の Issue にしてリンクする。
4. 技術の設計（データモデル・API・置き場所・ライブラリの選定）は、本文に書かない。最初の子（最小の 1 本）が、作業の最初に決める。親が調べた範囲だけで決めた設計は、子の作業を縛り、子が実装で分かったことを反映できなくなるから。全体に関わる構造（層の境界・データの形・外部との接続）も、最初の子が決める。
5. 書いた計画を、次の 4 つで見直す。
   - 完了の状態の変化は 1 つか。別々に受け入れ・延期できる成果が混ざっていたら、分けて、外した成果を backlog の Issue にする。例: 「CSV を取り込みたい。毎晩の自動同期も欲しい」なら、取り込みを Epic にし、自動同期を backlog の Issue にする。
   - 最初の子は最小の 1 本か。
   - 各子は 4 時間に収まるか。1 時間に満たない見込みの作業は、依存関係の近い次のストーリーと束ねる（4 時間と 1 時間は仮の値）。
   - 同じファイルやインターフェースを触るノードどうしに、依存の線を引いたか。
6. 調べた結果、全体が 4 時間以内で閉じると分かったら、Epic のまま計画しない。Epic の type を Task に書き換え、受け入れ条件を書き、Epic に「Task に書き換えた。窓口が起動する」とコメントしてから、利用者に窓口へ渡すことを伝える。子の Issue は立てない。

## 利用者との合意

利用者に、目的・完了の状態・全体の流れ（利用者の流れと依存グラフ）への合意を求める。返事には、合意してほしい中身を本文で書き、Epic の URL を添える。名前・置き場所・実装の方針のような細部は聞かない。推しで決め、選んだものと理由を返事に書く。

合意をもらうまで、子の Issue を立てず、worker を起動しない。合意の返事（「その計画でよいです」など）を受けたら、依存グラフで先行が無いノードだけを、続けて [S4](epic-s4.md) の手順で起動する。
