# ワーカーを起動する spec の型

窓口と Epic の親は、以下の型に実際の番号とパス、Issue ごとの作業時間の目安（例: 2 時間、4 時間）を入れ、報告先を 1 つ選んで担当するワーカーに渡す。

```text
Issue: <owner>/<repo>#<作業 Issue の番号> を担当する。受け入れ条件は Issue の本文を読む。
報告先: このワーカーを起動した coordinator に報告する（Epic #<番号> の親、または単独タスクを担当する窓口）。
決まり:
- 割り当てられた worktree で作業する。Orca が worktree の指定を求めたら、path:<worktree の絶対パス> を使う。リポジトリが違うと同じ Issue 番号が重なるため。
- セッションに何かを送る前に、同じ全文を作業 Issue にコメントする。利用者には話しかけない。作業を止める依存や利用者の判断が必要なら、コメントしてから ask で coordinator に上げ、ターンを終える。
- 範囲外の作業に着手せず、作業 Issue の子を立てない。Epic の完了に要る残りは、作業 Issue にコメントして ask で親に戻す。要らない残りや単独タスクの残りは backlog Issue に置く。
- 作業時間が <この Issue の作業時間の目安> を超える見込みなら、受け入れ条件を完了した範囲に書き換える。外した範囲が Epic の完了に要るなら作業 Issue にコメントして ask で親に戻し、要らなければ backlog Issue に置く。単独タスクの残りも backlog Issue に置く。
- 設計・実装・テストは自分で進める。仕上げのレビューと読むだけで済む調べものにはサブエージェントを使ってよいが、ファイルは書き換えさせない。
閉じ方:
- PR に hold-merge が付いていれば、勝手にマージしない。承認が作業の完了に必要なら、作業 Issue に確認したい内容をコメントしてから ask で coordinator に上げる。
- 完了した範囲のマージを済ませ、作業 Issue に「片付いたこと・片付かなかったこと・計画に影響する発見」をコメントする。次に作業 Issue を閉じ、worker_done を送る。完了した範囲を示せなければ Issue を開いたままにし、理由を報告して worker_done を失敗として送る。
- worktree は worker_done を受けた coordinator が片付ける。
```

## issue-planning のスキル本文を書くワーカー

親は、スキルの本文を書く子の起動前に[評価器の手順](../evals/README.md#スキルを書くワーカーの起動と確認)に従い、子の worktree から最終評価データセットを外してプロジェクトのフックを有効にする。
