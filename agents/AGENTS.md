## APIキー
- 作業はリモートが基本で `op` のGUI認証が通らないため、エージェントは1Passwordの Service Account 経由でキーを取り出し、ローカルの `.env` に置いて使う
- 全プロジェクト共通のキー（`OPENAI_API_KEY` / `TYPESAFE_API_KEY` 等）は `~/.env` に置く。シェル起動時に読み込まれる。足りなければ `cd ~ && op-env <キー名>` で書き足す。アプリが使う Anthropic のキーは、`~/.env` にもプロジェクトの `.env` にも `ANTHROPIC_API_KEY` 以外の名前で置く（例: `op-env APP_ANTHROPIC_API_KEY=ANTHROPIC_API_KEY`）。この名前でシェルにあると、Claude Code は非対話（`-p`）では必ず、対話では一度承認するとそれ以後、サブスクではなくそのキーで動き、API の従量課金になるから
- プロジェクト固有のキーは、エージェントが自分で `op-env KEY1 KEY2 ...` を実行してプロジェクトルートの `.env` に書く。読む先は `op://Dev/<キー名>/credential`（`Dev` vault、アイテム名は環境変数名と同じ）。`op-env` は既存の `.env` の同名キーだけを置き換え、値をシングルクォートで囲んで書き、600 にする。値が空・シングルクォートや改行やバックスラッシュを含むキーは書かずに止まる。`.env` がシンボリックリンクならリンク先に書く
- アイテム名が環境変数名と違うときや、`credential` 以外のフィールド（`username` など）を読むときは `op-env NAME=ITEM/FIELD` と書く（`FIELD` を省くと `credential`）。例: helix-saas の管理画面のログインに使う Google の OAuth クライアントは `op-env IDP_CLIENT_ID=GCP_HELIX_IDP_CLIENT_ID IDP_CLIENT_SECRET=GCP_HELIX_IDP_CLIENT_SECRET`。トークンを読んで `op read` を直接打たない
- `.env` は `mise.toml` の `[env]` に `_.file = ".env"` を書いて読み込む。zsh・fish はどちらも `mise activate` しているので、プロジェクトに `cd` したシェルには自動で入る。シェルを通さずに起動するコマンドで値が要るときは `mise x -- <コマンド>` で実行する
- キー名だけを並べた `.env.example` をコミットする。`.env` はコミットしない（グローバル gitignore で除外済み）
- `op-env` が「読めなかったキー」を返したら、値を探したり作ったりせず、そのキー名を利用者へ伝えて止まる（`Dev` vault への登録は利用者がする）。会話に値を貼ってもらわない
- キーの値をコード・会話・ログ・コミットに出さない。`.env` やトークンファイルを `cat` 等で表示しない。キー名の確認は `cut -d= -f1 .env`、値の有無の確認は長さだけ（例: `${#OPENAI_API_KEY}`）
- `OP_SERVICE_ACCOUNT_TOKEN` をシェルに export しない（手元の `op` が Service Account に切り替わり `Personal` vault を読めなくなる）。トークンは `op-env` だけが `~/.config/op/service-account-token` から読む
- `op-env` は 1Password へのネットワーク接続が要る。サンドボックス内で接続できないときはサンドボックス外で実行する
- クラウド環境（手元のMacでない実行環境）ではトークンも `.env` も無いので、その環境の設定で環境変数を渡す

## 書き方
- 図は ASCII アートでなく Mermaid で描く（GitHub でそのまま表示される）
- 前提はぼかさず言い切る（「〜に依存するので例示に留める」と書かず、「既定は X、同等の機能があれば Y も可」と書く）。読み手が同じ判断を再現できなくなるから
- 文章から組み立て直せない仕組み（lint のセレクタ、型での強制など）はコード例で示す。分量を理由に落とさない
- 文書には、今日の行動を変える記述だけを置く。コードを読めば分かることの書き写し・もう無い物の説明・進捗は書かない。コードが変わっても文書は置いていかれるので、読み手が実態とずれた前提で動いてしまう（必要になったら git の履歴で読める）
- 決定の経緯（「決着済み」「再検討しない」など）を文書に溜めない。状況が変わっても前提として読まれ続け、次の判断を縛る。理由はコミットや PR に残す
- ルールは1箇所に集めず、それを必要とする仕組みの隣（検査が落ちる設定ファイルやワークフローなど）に置く。離れていると、落ちた人が理由に辿り着けないし、仕組みだけが変わってずれていく
- 規則を足すときは、先に機械で判定する方法を考える。lint・型・テスト・CI の検査・フックのどれかで判定できるなら、文章でなくその検査として足し、理由は検査の設定やエラーメッセージに書く。文章の規則は読み落とせば効かず、守れているかを人やレビューが毎回確かめることになるから。機械で判定できない部分だけを文章に残す。例: 「unit テストで HTTP をモックするライブラリを使わない」は、文章で書かずに ESLint の `no-restricted-imports` で止める
- 会話の中で作った言葉（呼び名・略称・比喩）は、会話の外の人が読む文書・画面・Issue に出す前に、定義を書くか、一般の言葉に戻す。書き手は会話の中にいるので、その言葉が通じない人がいることに気づけない
- 作業の中（ツールの実行・ファイル）で付けた ID や名前（画面の番号、型の値など）は、利用者には見えていない。返事では ID だけで指さず、それが何かを名前で言う。ID は名前に添える程度にする
- 返事は、利用者の問いへの答えか、決めてほしいことを先頭に置き、作業の報告はその後に短く書く。報告・提案・質問を 1 通に詰めると、質問が埋もれて拾えない
- 決めてほしいことは、判断に要る中身（本文・選択肢・例）をその場に書く。「上の本文」「前に聞いた件」のように離れた場所を指さない。読み手が前の返事を探し直すことになり、どれのことか分からなくなる
- 抽象的な提案には具体例を 1 つ添える。何を数えたか・測ったかを言わずに、数や判断だけを出さない
- 短くするために、主語・目的語・前提・具体例を削らない。読み手が一度読んで分かることを、短さより優先する
- 消すかどうかは、中身を読んでから決める。参照数などの見た目で判定すると、生きているものを消してしまう
- 規律は NEVER・MUST みたいな大文字の命令形で書かず、何をするか（しないか）と理由を添えた文で書く。強調すると効きすぎて、関係ない場面まで縛ってしまう。それに理由が無いと、想定外の場面で読み手が判断できない
- 指示書（AGENTS.md・CLAUDE.md・スキルなど）に書き込むときは、入れる本文を見せて OK をもらってから書く。方針に合意しても、文面そのものが論点になることが多いから

## 進め方
### 作る意味があるものだけを作る
作る・足す前に次の 3 つに答える。答えられなければ作らない。
- 何の困りごとを解くか。それは実際に起きているか（「起きうる」ではなく）
- 作らずに済まないか。既存の仕組み・組み込みの機能・確立したツール・手作業の手順で足りないか
- 作ったものを誰がいつ使うか

作っている途中でも同じ問いを当て直す。次の状態は、作る意味が無いものを作っている合図になる。
- 直す周回が終わらず、新しい指摘の原因が自分の足した部分にある
- 守ろうとしているのが、実際には起きない入力ばかりになった
- 本命の仕組みが既に止めているものを、補助で重ねて止めようとしている

合図が出たら作り込むのをやめ、捨てる案を利用者に出す。

### 最上位の大きなものから考える
何を作るときも、上位から順に決めて合意し、それから下へ降りる。
1. 目的と前提：何のために・誰のために作るか、何をもって成功とするか（プロジェクト憲章や北極星にあたるもの）
2. 全体の流れ：業務システムなら業務の流れ、提案書ならアジェンダ、開発の仕組みなら開発の工程
3. 細部：個々の部品・機能・文面

着手するときは、まず上位のもの（プロジェクト憲章・北極星・全体の流れ図など）が既にあるかを確かめる。無い・古い・目の前の作業と合わない、のどれかなら、細部に入る前にそれを作るか見直す提案をする。上位が無いまま下を決めると、何のための部品・質問なのかが分からない。しかも後で上位に合わなくなって、作り直しになる。

### 最初に短い流れを 1 本だけ全部の層に通し、その後は利用者の操作順に作る
作るものを分けて順に進めるときは、最初に、利用者の流れを 1 本だけ、いちばん短い形で、画面・API・認証・データ・デプロイの全部の層に通して動かす（Cockburn の walking skeleton）。業務アプリなら「開く → ログインする → ホームが表示される」の 1 本で、ホームの中身は空でよい。ほかの機能は作らない。置き場所・認証との連携・画面の枠のように全体に関わる決定は、後から変えるほど作り直しが広がる。中身が少ないうちに決めて動かせば、つながらない箇所が安く見つかる。そのうえ、後の機能をこの上に並行して作れる。

その後は、利用者が操作する順（サインアップ → サインイン → ホーム → 主な業務）に分けて作る。前の操作ができていないと、後の操作を最初から通しで試せないから。

### 計画は親 Issue に持たせ、作業は 4 時間で閉じる子 Issue に割る
大きな目的ごとに親 Issue を1つ立て、その目的・完了の状態・計画（ストーリーの一覧と順序）を本文に書く。作業は親の sub-issue（子 Issue）に割り、親にはセッションを当てない。計画と進み具合は親の本文と子の一覧の 1 か所で見られ、子は小さいまま閉じられるから。4 時間で閉じる作業は、親を作らずに子 Issue と同じ決まりの単独の Issue にする。
- 子 Issue は、受け入れ条件のストーリーをちょうど 1 つ持ち、1 つのスタックで片付け、着手から 4 時間以内に閉じられる大きさにする。4 時間で閉じる見込みが立たなければ、着手する前に割る。着手した後に 4 時間を超えそうになったら延ばさない。片付いた分で閉じ、残りは新しい子に切り出して親の計画に戻す。セッションの文脈は長くなるほど答えが劣化し（Chroma の context rot）、エージェントが確実にこなせるタスクの長さにも限りがある（METR の time horizon）。人の開発でも、数時間ぶんの小さいバッチで出すほうが速く安定して届く（DORA の working in small batches）
- 途中で見つかった作業は、今の子のストーリーの受け入れ条件に要るものだけ今の子に入れる。それ以外は親に新しい子として足し、今のセッションでは手を付けない。何でも今の子に足すと子が育ち、4 時間で閉じられなくなるから
- 計画（やること・順序・子の切り方・進み具合）はリポジトリのファイルに書かず、親 Issue と子 Issue にだけ置く。リポジトリに置くのは、計画が終わった後も読まれ続ける決まり（仕組みの使い方・規則とその理由）だけにする。計画をファイルに置くと、Issue と二重になってずれるうえ、閉じた後も前提として読まれ続けるから
- 完了の状態（受け入れ条件）は、利用者のストーリー（「〜として、〜したい」）ごとに束ね、その下に観測できる確認項目を置く。検査項目を並べるだけだと、誰の何が解決したら終わりなのかが読めない。そうなると、項目を全部満たしても目的を外しうる。CI が通るといった全作業に共通の決まりは、ストーリーに入れず別に並べる
- PR は実測で割る。作業の途中で `git diff --stat` を見て、手で書いた変更行が 400 行を超えたら、CI が通る位置で区切る。区切った PR は GitHub のスタックド PR（`gh stack`）で積み、下の PR のマージを待たずに上の層の作業を続ける。削除だけの行・生成物（lock ファイル・dist など）・機械的な置換（リネーム・一括整形）は数えない。400 行に届かなくても、互いに関係ない変更が混ざっていたら層を分ける。1 つの子 Issue から出すのは 1 つのスタックだけにする。スタックの層の数に決まりは無い。スタックは 1 つの流れとして `gh stack` で管理できるから。大きい変更ほどレビューで欠陥を見逃すことは、Mozilla の分析（Kononenko 2015）と統制実験（Baum 2019）で同じ向きに出ている。変更するファイルが多いほど、役に立つレビューコメントの割合が下がることも分かっている（Bosu 2015）。AI エージェントの PR でも、大きいものほどマージされにくい（Ehsani 2026。効果は小〜中で、CI の失敗のほうが強く効いていた）。一方で 400 行という線は、SmartBear が Cisco の 1 グループのデータから出した推奨（200 行未満が望ましく、400 行が上限）で、ほかの研究では確かめられていない。だから上限の目安として使い、小さく出せるなら小さく出す
- スタックの各層は、CI が通り、その層までをマージしても既存の動きを壊さない単位にする。子 Issue のストーリーは、各層ではなくスタック全体で片付ける。API だけ・画面だけの層は、それだけでは誰も使わない変更になるから。層は依存の順に積み、下に土台（データモデルなど）を置く。マージは承認された層から、下から順に 1 層ずつ `gh stack merge <PR 番号>` で行い、自動マージは使わない。マージは層ごとに先に確認するから。マージしたら `gh stack sync` で残りの層を main に載せ直す。main を Restrict updates で守っていて `gh stack merge` が「Cannot update this protected ref」で止まるリポジトリでは、`gh api --method PUT repos/<owner>/<repo>/pulls/<番号>/merge-async -f merge_method=squash -f sha=<head の SHA> -F bypass_rules=true` で一番下の層を入れる。GitHub は bypass でのマージを一番下の PR にしか許さないので、下から 1 層ずつ入れる
- 作業用ブランチでは、commit・push・PR の作成と ready 化を、そのつど確認せずに進める。確認を挟むと作業が止まり、毎回同じ承認を求めることになるから。マージ・force push・履歴の書き換え・削除は戻しにくいので、先に確認する。自分のスタックの作業用ブランチを rebase して `gh stack push`・`gh stack sync` で押し直すのは、中身は force push だが確認せずに進める。スタックでは下の層を直すたびに上の層の rebase が要り、毎回止めると積む意味がなくなるから
- 1 つのスタックで `gh stack` を打つのは、同時には 1 セッション（持ち主）だけにする。`gh stack sync`・`gh stack push` は fetch した直後のリモートを基準に force push するので、別のセッションが同じブランチへ押したコミットを警告なしで上書きする。別のセッションに層を任せるときは、そのセッションは `gh stack` を使わずに自分の層のブランチを普通に push して PR を作る。持ち主がそのブランチを rebase したら、`git fetch` のあと `git rebase origin/<ブランチ>` で追いついてから押す（force push はしない）。取り込むのは持ち主が `gh stack link <スタック番号> <PR 番号>` → `gh stack sync` で行う

### 調べてから組み、測り方は先に決める
- 確立した分野（統計・機械学習・アノテーション・セキュリティなど）にあたる作業は、着手する前にその分野の定石を調べる。手順は出典（論文・教科書・公的なガイドライン）付きで示してから進める。自己流で組んだ手順には、その分野が既に潰した誤りが残っている
- 何かの良し悪しを測る仕組み（スキルやプロンプトの評価、判定器、ベンチマークなど）を作るときは、指標・合格線・判定基準を、データや結果を見る前に決めて利用者と合意する。外れたケースに合わせて基準を後から直すと、基準が手元のデータに寄ってしまい、測った数字が別のデータでは再現しない。基準を直す必要が出たら、直した基準で全ケースを測り直し、それより前の数字とは比べない
- 変更の効果を数字で報告するとき（評価の通過率・所要時間・トークン数など）は、同じ条件で繰り返したときのばらつきの幅も測り、差と並べて示す。LLM の出力は同じ入力でも毎回揺れるので、1回ずつ比べただけでは、効果とばらつきを見分けられない。ばらつきより小さい差は「改善」と書かず、「差は見えなかった」と書く

### ワーカーのモデルは作業の種類と使用量で選ぶ
Orca などでワーカーを立てるときは、作業の種類で次のようにモデルを選ぶ。
- 設計（構造・境界・計画）は、Opus 5.5 か GPT-6.1 Sol のうち、サブスクの使用量に余裕がある方にする。両方のサブスクを使い切り、超過課金を減らすため
- 仕上げのレビューは、書いたワーカーと別の会社のモデルにする（Claude が書いたら `codex review`、Codex が書いたら Claude の `/code-review`）。同じ系統のモデルは同じところを見落としやすいから。どちらのモデルが実装しても、欠陥はここで拾う
- 仕様が決まっている実装と受け入れテストは、GPT-6.1 Sol か Sonnet 5.5 のうち、サブスクの使用量に余裕がある方にする。両方のサブスクを使い切り、超過課金を減らすため
- 機械的な修正（lint の指摘直し・リネームなど）は、Haiku 5.5 か GPT-6.1 Terra のうち、使用量に余裕がある方にする。速く、使用量も少なく済むから
- ワーカーを立てる前に `agent-usage` で、Claude と Codex の使用率・リセット日時・最終取得日時を見る。週の使用率が低い方へ振り、差が5ポイント以内なら、両方で比較できる5時間枠など、より短い期間の使用率が低い方を選ぶ。古い値・取得不可の値では比較せず、その側のセッションで応答後に再確認する。比較できる値が揃わなければ、そのことを利用者に伝える
- レビューの P0/P1 の指摘が片方のモデルにだけ目立って多いときは、使用量で振るのをやめて利用者に伝える

### セッションと worktree は Issue ごとに分ける
1 つの子 Issue（親を作らない単独の Issue を含む）に 1 つのセッションと worktree を当てる。親 Issue には当てない。1 つのセッションに複数の Issue を積むと、質問と報告が混ざるから。
- 既定のブランチ（`main` など）の作業ツリーのセッションは、質問に答える・読んで調べる・Issue を立てる・別のセッションに渡す、だけをする。ファイルを変える作業は 1 行でも、確認を挟まずに Issue を立て、`orca worktree create --name issue-<番号> --issue <番号> --agent <エージェント> --prompt <メモ>` で渡す。既定のブランチに変更が残ると、worktree の作成や `git pull` の邪魔になるから
- Orca のワーカーは、Issue のセッションがその中の作業を並べたいときだけ立てる。既定のブランチのセッションが立てると、完了を待つ間に利用者へ答えられなくなるから。同じ理由で、ワーカーを立てたセッションは指示・承認の中継・まとめだけをし、PR の main の取り込み・CI の待ち・マージは、その PR を作ったワーカーにさせる。マージの承認は、ワーカーの `ask` を利用者に確認して `orca orchestration reply` で返す
- 別のセッションに引き継ぐ前に、立てたワーカーを全部報告させきる。前のセッションのワーカーには、新しいセッションから `send` できないから。メモには、Issue の番号・worktree とブランチと PR・進み具合と次の作業・Issue にまだ書いていない利用者の決定・確認待ちのこと、だけを書く。計画を書き写すと Issue とずれるから
- Issue が閉じたら、その Issue のセッションが、未コミットの変更が無い・push 済み・PR がマージ済みか閉じている、を確かめて利用者に聞き、OK なら最後の操作として `orca worktree rm --worktree issue:<番号> --delete-branch` で消す。`--force` は未コミットの変更を捨てるので使わない
- Orca の中から `claude -p`・`codex exec` を入れ子で起動するときは、`orca-nested claude -p "..."` のように `orca-nested` を通す。`ORCA_` の環境変数を受け継ぐと、入れ子の終わりを Orca がワーカーのターンの終わりと取り違えるから
