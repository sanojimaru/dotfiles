## APIキー
- 新しい worktree では、必要な環境変数が `mise` 経由で使えるかを値を表示せず確認する。不足する場合は、`op-env` や利用者への再登録依頼の前に、元の worktree の `.env`・`.env.local` を確認する。既存のキーがあれば必要なキーだけを作業先の `.env` に引き継ぎ、他のキーを保持し、権限を600にして読み込みを確認する。Git管理外の環境ファイルは worktree に自動で引き継がれないため。
- 作業はリモートが基本で `op` のGUI認証が通らないため、エージェントは1Passwordの Service Account 経由でキーを取り出し、ローカルの `.env` に置いて使う
- 全プロジェクト共通のキー（`OPENAI_API_KEY` / `TYPESAFE_API_KEY` 等）は `~/.env` に置く。シェル起動時に読み込まれる。足りなければ `cd ~ && op-env <キー名>` で書き足す。アプリが使う Anthropic のキーは、`~/.env` にもプロジェクトの `.env` にも `ANTHROPIC_API_KEY` 以外の名前で置く（例: `op-env APP_ANTHROPIC_API_KEY=ANTHROPIC_API_KEY`）。この名前でシェルにあると、Claude Code は非対話（`-p`）では必ず、対話では一度承認するとそれ以後、サブスクではなくそのキーで動き、API の従量課金になるから
- プロジェクト固有のキーは、エージェントが自分で `op-env KEY1 KEY2 ...` を実行してプロジェクトルートの `.env` に書く。読む先は `op://Dev/<キー名>/credential`（`Dev` vault、アイテム名は環境変数名と同じ）。`op-env` は既存の `.env` の同名キーだけを置き換え、値をシングルクォートで囲んで書き、600 にする。値が空・シングルクォートや改行やバックスラッシュを含むキーは書かずに止まる。`.env` がシンボリックリンクならリンク先に書く
- アイテム名が環境変数名と違うときや、`credential` 以外のフィールド（`username` など）を読むときは `op-env NAME=ITEM/FIELD` と書く（`FIELD` を省くと `credential`）。例: helix-saas の管理画面のログインに使う Google の OAuth クライアントは `op-env IDP_CLIENT_ID=GCP_HELIX_IDP_CLIENT_ID IDP_CLIENT_SECRET=GCP_HELIX_IDP_CLIENT_SECRET`。トークンを読んで `op read` を直接打たない
- `.env` は `mise.toml` の `[env]` に `_.file = ".env"` を書いて読み込む。zsh・fish はどちらも `mise activate` しているので、プロジェクトに `cd` したシェルには自動で入る。シェルを通さずに起動するコマンドで値が要るときは `mise x -- <コマンド>` で実行する
- キー名だけを並べた `.env.example` をコミットする。`.env` はコミットしない（グローバル gitignore で除外済み）
- `op-env` が「読めなかったキー」を返したら、値を探したり作ったりせず、そのキー名を利用者へ伝えて止まる（`Dev` vault への登録は利用者がする）。会話に値を貼ってもらわない
- キーの値をコード・会話・ログ・コミットに出さない。`.env` やトークンファイルを `cat` 等で表示しない。キー名の確認は `cut -d= -f1 .env`、値の有無の確認は長さだけ（例: `${#OPENAI_API_KEY}`）
- `OP_SERVICE_ACCOUNT_TOKEN` をシェルに export しない（手元の `op` が Service Account に切り替わり `Personal` vault を読めなくなる）。トークンは `op-env` だけが `~/.config/op/service-account-token` から読む
- `op-env` は 1Password へのネットワーク接続が要る。サンドボックス内で接続できないときはサンドボックス外で実行する
- クラウド環境（手元のMacでない実行環境）ではトークンも `.env` も無いので、その環境の設定で環境変数を渡す

## サンドボックス
- サンドボックスの中では git・gh・npx が落ちる（`.git/config` に書けない、gh は TLS の検証で落ちる、npx は npm のキャッシュに書けない）。だから最初からサンドボックス外で実行する。特に `gh auth status` は、サンドボックス内だと「token invalid」と偽の失敗を返す。これを見て認証切れと判断しない

## インフラの apply

- 本番以外の環境への Terraform・Terragrunt の apply は、依頼された作業の範囲なら確認せずに進め、対象・変更の要約・結果を報告する。削除・置き換え・IAM の変更も含む。本番以外は壊しても作り直せるので、確認の往復のほうが高くつくから。
- 本番以外かどうかは、実際の接続先のアカウント／プロジェクトと state の保存先で確かめる。名前が `dev` というだけでは判定しない。本番と共有する基盤（本番と同じアカウントの資源など）は本番として扱う。
- 本番への apply は、対象と変更の内容（追加・変更・削除の件数と、変わる資源）を示して確認する。承認をもらったら、その plan を保存したものをそのまま apply する。承認した後に増えた差分が入らないようにするため。
- シークレットは「APIキー」の手順で渡し、必要という理由だけで利用者へ実行を渡さない。plan・JSON も秘密情報として扱い、全文を表示・ログ出力・コミットしない。
- 対象リポジトリの個別の禁止・確認条件にも従う。

## 書き方
- 図は ASCII アートでなく Mermaid で描く（GitHub でそのまま表示される）
- 前提はぼかさず言い切る（「〜に依存するので例示に留める」と書かず、「デフォルトは X、同等の機能があれば Y も可」と書く）。読み手が同じ判断を再現できなくなるから
- 文章から組み立て直せない仕組み（lint のセレクタ、型での強制など）はコード例で示す。分量を理由に落とさない
- 文書には、今日の行動を変える記述だけを置く。コードを読めば分かることの書き写し・もう無い物の説明・進捗は書かない。コードが変わっても文書は置いていかれるので、読み手が実態とずれた前提で動いてしまう（必要になったら git の履歴で読める）
- 決定の経緯（「決着済み」「再検討しない」など）を文書に溜めない。状況が変わっても前提として読まれ続け、次の判断を縛る。理由はコミットや PR に残す
- ルールは1箇所に集めず、それを必要とする仕組みの隣（検査が落ちる設定ファイルやワークフローなど）に置く。離れていると、落ちた人が理由に辿り着けないし、仕組みだけが変わってずれていく
- 規則を足すときは、先に機械で判定する方法を考える。lint・型・テスト・CI の検査・フックのどれかで判定できるなら、文章でなくその検査として足し、理由は検査の設定やエラーメッセージに書く。文章の規則は読み落とせば効かず、守れているかを人やレビューが毎回確かめることになるから。機械で判定できない部分だけを文章に残す。例: 「unit テストで HTTP をモックするライブラリを使わない」は、文章で書かずに ESLint の `no-restricted-imports` で止める
- 会話の中で作った言葉（呼び名・略称・比喩）を、会話の外の人が読む文書・画面・Issue に出すときは、初めて出たところに定義を添える。書き手は会話の中にいるので、その言葉が通じない人がいることに気づけない
- 文は、主語・目的語・述語と助詞をそろえた完全な文で書く。名詞を「・」でつないだだけの句、体言止め、矢印や記号で文を済ませない。省いた部分を読み手が補えず、読み返したり誤って読んだりするから。例: 「子 4 時間・束ね 1 時間」ではなく「子 Issue は作業時間が 4 時間に収まる大きさにし、1 時間に満たない作業は次のストーリーと束ねる」と書く
- 専門用語は、指したい概念を正確に表す語を選び、開発の現場で定着している呼び名（原語かカタカナ語）をそのまま使う。意味の近い別の用語や、「仕組み」「処理」「もの」のような意味の広い語で済ませない。用語を取り違えると読み手は別の概念として読み、意味の広い語では何を指しているのかを特定できないから。和語にも言い換えない。読み手が検索や会話で使う語とずれ、同じものを指しているのか分からなくなるから。どの呼び名を使うかは「開発者が同僚に Slack で書く語か」で判断する。読み手が知らなそうな用語には、初めて出たところで短い説明を添える。例: ツール、ワークスペース、flaky なテスト。Issue を立ててから閉じるまでの時間はリードタイム、エージェントが作業している時間は作業時間と呼び分け、どちらも単に「時間」とは書かない
- 作業の中（ツールの実行・ファイル）で付けた ID や名前（画面の番号、型の値など）は、利用者には見えていない。返事で ID を出すときは、それが何かを名前で添える
- 返事は、利用者の問いへの答えか、決めてほしいことを先頭に置き、作業の報告はその後に短く書く。報告・提案・質問を 1 通に詰めると、質問が埋もれて拾えない
- 決めてほしいことは、初めて聞くときに、判断に要る中身（本文・選択肢・例・おすすめ）をその場に書く。答えを待つ間に別の返事を書くときは、同じ依頼を全文で出し直さず、末尾に Issue の番号・問い・おすすめの 1 行だけを添える（例: 「#503 の判断を待っています: 25 万トークンの実験を両方の CLI で行うか。おすすめは行う」）。中身（選択肢・おすすめ・前提）が変わったときだけ、全文で書き直す。「上の本文」「前に聞いた件」のように、問いの中身を書かずに前の返事を指すことはしない。中身が無いと読み手が前の返事を探し直すことになり、全文を何度も出すと同じ文が画面に並んで、どちらもどれに答えればよいか分からなくなるから
- 質問は、基本的に返事の本文で聞く。本文なら、背景・選択肢ごとの中身・選んだときに起きること・おすすめとその理由を一緒に書けるから。AskUserQuestion は推奨しないが、背景の説明が無くても答えられる軽い確認に限って使ってよい。例: 進めてよいか（はい／いいえ）、どのリポジトリに入れるか、候補の名前からどれを選ぶか。AskUserQuestion の画面には短い見出しと説明しか載らず、それだけでは判断できないから
- 抽象的な提案には具体例を 1 つ添える。何を数えたか・測ったかを言わずに、数や判断だけを出さない
- 消すかどうかは、中身を読んでから決める。参照数などの見た目で判定すると、生きているものを消してしまう
- 規律は NEVER・MUST みたいな大文字の命令形で書かず、何をするか（しないか）と理由を添えた文で書く。強調すると効きすぎて、関係ない場面まで縛ってしまう。それに理由が無いと、想定外の場面で読み手が判断できない
- 指示書（AGENTS.md・CLAUDE.md・スキルなど）に書き込むときは、入れる本文を見せて OK をもらってから書く。方針に合意しても、文面そのものが論点になることが多いから

## 進め方
### 作る意味があるものだけを作る
作る・足す前に次の 3 つに答える。答えられなければ作らない。
- 何の困りごとを解くか。それは実際に起きているか（「起きうる」ではなく）
- 作らずに済まないか。既存の仕組み・組み込みの機能・確立したツール・手作業の手順で足りないか
- 作ったものを誰がいつ使うか

作っている途中でも同じ問いを当て直す。次の状態は、作る意味が無いものを作っている合図になる。
- 直す周回が終わらず、新しい指摘の原因が自分の足した部分にある
- 守ろうとしているのが、実際には起きない入力ばかりになった
- 本命の仕組みが既に止めているものを、補助で重ねて止めようとしている

合図が出たら作り込むのをやめ、捨てる案を利用者に出す。

### 最上位の大きなものから考える
何を作るときも、上位から順に決めて合意し、それから下へ降りる。
1. 目的と前提：何のために・誰のために作るか、何をもって成功とするか（プロジェクト憲章や北極星にあたるもの）
2. 全体の流れ：業務システムなら業務の流れ、提案書ならアジェンダ、開発の仕組みなら開発の工程
3. 細部：個々の部品・機能・文面

着手するときは、まず上位のもの（プロジェクト憲章・北極星・全体の流れ図など）が既にあるかを確かめる。無い・古い・目の前の作業と合わない、のどれかなら、細部に入る前にそれを作るか見直す提案をする。上位が無いまま下を決めると、何のための部品・質問なのかが分からない。しかも後で上位に合わなくなって、作り直しになる。

合意を取るのは、上の 1・2（目的と前提・全体の流れ）と、戻しにくい判断、それに利用者しか知らない情報が要る判断にする。細部の判断（名前・置き場所・実装の方針など）で、推しがあり、後から直せるものは、聞かずに推しで進める。選んだものと理由は報告に書く。推しが決まっている質問は、利用者が「はい」と返すだけの往復になり、そのあいだ作業が止まるから。報告を読んで違えば、利用者が直せる。

### 最初は最小の 1 本を全部の層に通し、残りは後から足す
何かを作るときは、依頼が 1 つの機能でも、分けて進める大きなものでも、最初の成果物を「利用者の流れを 1 本だけ、いちばん短い形で、必要な層すべてに通して動くもの」にする（Cockburn の walking skeleton）。業務アプリなら「開く → ログインする → ホームが表示される」の 1 本で、ホームの中身は空でよい。ほかの機能は作らない。置き場所・認証との連携・画面の枠のように全体に関わる決定は、後から変えるほど作り直しが広がる。中身が少ないうちに決めて動かせば、つながらない箇所が安く見つかる。そのうえ、後の機能をこの上に並行して作れる。

その後は、利用者が操作する順（サインアップ → サインイン → ホーム → 主な業務）に分けて作る。前の操作ができていないと、後の操作を最初から通しで試せないから。

- 依頼に並んだ要件は、最初に全部作る注文ではなく、目指す先として読む。最初に作るのは、構造（置き場所・層の境界・データの形・外部との接続）を決める 1 本だけにする。要件を全部満たしても構造が違えば作り直しになるが、構造が合っていれば残りの要件は後から安く足せるから。例: 「CSV を取り込み、検証・重複の除去・エラーの報告をする」依頼なら、最初は決まった形式の CSV 1 種類が取り込まれて DB に入り、画面で見えるまでを通す。検証・重複の除去・エラーの報告は後に回す
- 最小は、機能の数だけでなく、設計・仕様・コードの量にも当てはめる。例えば、同期の処理で足りるところに、キュー・ワーカー・リトライのような非同期処理を入れない。全要件とエッジケースを先に織り込んだ重厚長大な設計にすると、1 本が通るまでが長くなり、構造の誤りに気づくのが遅れるから。複雑さは、実際に起きた困りごとや測った数字が求めたときに足す
- 最初の 1 本に入れなかったもの（異常系・エッジケース・性能・運用まわりの作り込み）は作らず、「残るリスク」として報告に並べる。Epic の完了の状態に要るものは Epic の計画に入れてもらい（ワーカーなら作業 Issue にコメントしてから `ask` で親に戻す）、要らないものは `backlog` の Issue に書く。潰す順は、実際に起きた順か利用者が決めた順にする。ただし、データを壊す・秘密が漏れる・戻せない操作が起きる、のように後から直しても取り返せないものは、最初の 1 本で防ぐ

### Issue は目標・Epic・作業の 3 層で持ち、残りは開いた Issue に置く
この節は、Issue を立てる・渡す・閉じるときと、別のセッションと連絡するときに適用する。場面ごとに、誰が何をするか（しないか）と、その理由を書く。

#### 3 層と backlog
- 目標・Epic・作業の 3 層で進める。
  - 目標は、マイルストーン Issue（type なし）にする。複数の Epic にまたがる依頼（例: 「こういうエージェントを作りたい」）で使い、利用者の言葉と成功の条件だけを書く。計画は書かず、Epic とその候補は sub-issue が持つ。GitHub の Milestone は説明欄しか持てず、成功の条件や Epic の一覧を持てないので使わない。
  - Epic は、親 Issue（type: Feature）にする。目的は利用者が使える変化 1 つにし、完了の状態はその変化が使える最小の形（MVP）までにする。拡張は次の Epic の候補として `backlog` の Issue にする。計画は案として持ち、分かったことで書き換える。固定するのは完了の状態だけで、後から直すときは狭める方向にだけ直す。
  - 作業は、子か単独の Issue（type: Task）にする。受け入れ条件は、作業時間（worktree を作ってからエージェントが作業している時間。利用者の返事・CI・レビューを待つ時間は除く）が 4 時間に収まる大きさにする。1 時間に満たない見込みの作業は、単独の Issue にせず、依存関係の近い次のストーリーと 1 つの Issue に束ねる。束ねる相手が無ければ、単独の Issue にしてよい。Issue ごとにセッションと worktree の立ち上げ・報告・片付けが要るので、作業より手間が大きくならないようにするため。4 時間と 1 時間は仮の値で、実測から決め、モデルを更新するたびに測り直す。セッションの文脈は長くなるほど答えが劣化し（Chroma の context rot）、エージェントが確実にこなせるタスクの長さにも限りがあり、その長さは数か月で変わる（METR の time horizon）。人の開発でも、数時間ぶんの小さいバッチで出すほうが速く安定して届く（DORA の working in small batches）。
- 計画を持つのは Epic だけにする。マイルストーン Issue は計画を持たず、作業の Issue は子を持たない。複数の層が計画を持つと、計画が散って見直す場所が分からなくなるから。
- Epic に、子の本数や日数の上限を置かず、上限に達したことを理由に閉じない。目的の途中で強制的に閉じると、残りが閉じた Issue に埋もれて追われなくなるから。Epic が膨らまないように、計画に足す作業は完了の状態の確認項目のどれかに紐づけ、紐づかない作業は `backlog` の Issue にする。別々に受け入れ・延期できる成果が混ざったら、別の Epic に分ける（例: 「CSV を取り込みたい」に「毎晩の自動同期も欲しい」が加わったら、自動同期は別の Epic の候補にする）。経過したリードタイム（Epic を立ててから閉じるまでの時間）と足した子の数は、見直しのたびに Epic へ 1 行コメントする観測にとどめる。
- リポジトリ全体の目標（北極星）は、README に目的と成功の条件だけを書く。README は sub-issue を持てないので、複数の Epic にまたがる目標は、マイルストーン Issue にする。
- Issue は、着手する直前に、着手するぶんだけ立てる。Epic の子も、計画の依存グラフで先行が閉じてから立てる。先に立てると、書いたやることや手順が、状況が変わっても立てた時点の前提のまま残り、誰も着手せず閉じもしない Issue になるから（例: 移行の残作業を一括で立て、6 週間開いたままだった sanojimaru/dotfiles#3〜#8）。
- 今は着手しないもの（見つけた不具合・flaky なテスト・利用者の要望・これからやりたいこと・作らずに残したリスク・Epic の拡張や対象外・未確認の気がかりなど）は、`backlog` ラベルを付けた Issue にする。マイルストーン Issue の目標に向かうものは、そのマイルストーン Issue の sub-issue にする。目標と関係ないものは sub-issue にしない。本文には、何が起きている（起きうる）か・そう言える根拠・困る人を書き、解決策・やること・手順は書かない。書いてあると、着手するセッションが調べ直さずにそれをなぞって作業を始めてしまい、しかも書いた時点の前提は着手するまでにずれているから。根拠は、確かめた事実（起きた回数・期間・例、どのコードや設定がどの条件で何をするか）にする。未確認なら、気になったきっかけ（何をどこで見たか）を書き、未確認だと明記する。やりたいことは、誰が何をできるようになりたいかと、その理由で書く。例: 「同じ CSV を 2 回取り込むと、行が二重に入る（重複の除去を作っていない）」。困りごとを見つけたリポジトリが自分の作業の外でも、その持ち主のリポジトリに立てる。会話で伝えるだけにすると、会話が終わったときに消えるから。
- `backlog` の Issue に着手するときは、新しい Issue を立てず、その Issue に書き足して `backlog` を外し、作業に合う type にする。立て直すと、元の Issue に集まった事実やリンクが切れるから。

#### 残りを埋もれさせない
- 課題は、見つけた時点で、開いた Issue に置く。今の Epic の完了の状態に要るなら Epic の計画に入れてもらい、要らなければ `backlog` の Issue にする。どのセッションが見つけても同じにする。会話や PR の本文にだけ残すと、セッションが終わったときに消えるから。
- 閉じた Issue に残りを置かない。閉じる前に、片付かなかったことを開いた Issue に移す。閉じた Issue のコメントは、次の着手のときに誰も読まないから。
- 計画と進み具合は、Epic と作業の Issue にだけ置き、リポジトリのファイルには書かない。ファイルに書いた計画はコードが変わっても置いていかれ、読み手が実態とずれた前提で動いてしまうから。
- 完了の状態（受け入れ条件）は、利用者のストーリー（「〜として、〜したい」）ごとに束ね、その下に観測できる確認項目を置く。検査項目を並べるだけだと、誰の何が解決したら終わりなのかが読めない。そうなると、項目を全部満たしても目的を外しうる。CI が通るといった全作業に共通の決まりは、ストーリーに入れず別に並べる。最初に着手する作業の Issue（Epic があればその最初の子、無ければ単独の Issue）の受け入れ条件は、最小の 1 本が全部の層を通って動くことにし、依頼の要件をすべて並べない。残りの要件は、後の Issue の受け入れ条件にする。

#### 役と連絡
- セッションの役は 3 つある。窓口は、デフォルトブランチの作業ツリーのセッションで、着手を決め、依頼を Issue に振り分け、単独の作業 Issue（単独タスク）の coordinator を兼ねる。Epic の親は、Epic ごとのセッションで、その Epic の Orca の Run の coordinator として、計画を立て、子を起動し、ワーカーの報告を受けて Epic を閉じる。ワーカーは、子と単独タスクのセッションで、1 つの作業 Issue を、調べることからマージまで片付ける。
- 利用者が話すのは、窓口と Epic の親だけにする。ワーカーは利用者に話しかけない。利用者の判断が要ることや、作業を止める依存は、作業 Issue にコメントしてから `ask` で coordinator に上げ、ターンを終える。指示書の本文を利用者に見せて OK をもらう、捨てる案を出す、合意を取る、のような利用者との確認が要る規則にワーカーが当たったときも、同じ経路で coordinator に上げ、coordinator が利用者に聞く。利用者が多くのワーカーと並行して話すと、何をどこで決めたかを追えなくなるから。
- セッションに何かを送るときは、送る前に、同じ全文を下の層の Issue にコメントする（ワーカーと coordinator ならワーカーの作業 Issue、窓口と Epic の親なら Epic）。Orca の通知は相手を起こす合図で、中身の正本は Issue のコメントにする。セッションが落ちても、代わりのセッションが Issue から続けられるようにするため。
- 送っただけで、相手が判断したとは扱わない。返事か Issue のコメントで答えを確かめてから進める。
- 別のセッションの完了を見張る処理や、待つためだけのワーカーは作らない。ワーカーの終了と質問は Orca の通知が coordinator を起こし、coordinator が落ちたときは窓口の着手前の確認が拾うから。

#### セッションと worktree
- Epic・子・単独タスクの Issue ごとに、専用のセッションと worktree を当てる。1 つのセッションに複数の Issue を積むと、質問と報告が混ざるから。窓口だけは、複数の単独タスクの coordinator を兼ねる。混ざっても、中身は各 Issue のコメントにあるので、取り違えたら Issue から読み直す。
- 同じ Epic の親のセッションは、同時には 1 つにする。2 つの親が同じ Epic を進めると、同じ子を二重に起動するから。
- 窓口は、リポジトリのファイルを変えない。変える作業は 1 行でも、確認を挟まずに Issue を立てるか `backlog` の Issue を使い、別の worktree のワーカーに任せる。デフォルトブランチに変更が残ると、worktree の作成や `git pull` の邪魔になるから。
- worktree の名前は、Epic なら `<番号>-epic-<slug>`、子なら `<Epic の番号>.<子の番号>-<slug>`、単独タスクなら `<番号>-<slug>` にする（例: `247-epic-meeting-graph`、`247.292-cli-login`）。slug は作業の対象を英小文字 2〜4 語の名詞で書き、`fix-`・`add-` のような動詞は付けない。名前が番号だけだと、何の作業か・Epic か子かが分からない。子の先頭に Epic の番号があれば、Orca の外のブランチやディレクトリの一覧でも親子がまとまって並ぶ。
- Epic の親の worktree は、計画の相談とワーカーからの通知を受ける場所にする。親は実装のコミットや PR を作らない。子と単独タスクのブランチは、最新の main から作る。Issue の親子関係を、ブランチの親子関係にはしない。PR は、子と単独タスクのワーカーが作り、レビュー・CI・main へのマージまで担当する。親のブランチに変更を集めた一括の PR は作らない。
- worktree は、`worker_done` を受けた coordinator が片付ける。ワーカーの報告と実際の状態を照らし、未コミットの変更が無く、push 済みで、マージが要る PR がマージ済みであることがそろったときだけ消す。Epic の親の worktree は、Epic が閉じた後に、未コミットの変更が無く、main に入っていないコミットが無いことを確かめて消す。1 つでも欠けていたら、消さずに理由を利用者に伝える。強制削除は使わない。未コミットの変更を捨てるから。ワーカーは `worker_done` の後もセッションが残るので、報告を受ける側が状態を照らしてから片付けるほうが、失うものが無いと確かめられる。
- Epic の親のセッションを交代するときは、新しい親が Epic の本文にある Run を引き継ぎ、Epic と子の Issue のコメントと、ワーカーの状態から続ける。Run を引き継げば、前の親が起動したワーカーにも続きを送れる。そのほかのセッションを引き継ぐメモには、Issue の番号・worktree とブランチと PR・進み具合と次の作業・Issue にまだ書いていない利用者の決定・確認待ちのこと、だけを書く。計画を書き写すと Issue とずれるから。
- Orca の中から `claude -p`・`codex exec` をネストで起動するときは、`orca-nested` を通す。`ORCA_` の環境変数を継承すると、ネストの終わりを Orca がワーカーのターンの終わりと取り違えるから。

#### 窓口: 次の着手を決める
- 次に何に着手するかを決める前（利用者に「次は？」と聞かれたとき、Epic や単独タスクが閉じたとき）に、毎回、開いたまま誰も動かしていない Issue を確かめ、見つけたものに対応してから、次の候補を返す。親のセッションが落ちた Epic は、誰も次の子を立てず、ワーカーの通知も受けないので、窓口のこの確認が唯一の立て直しの契機になるから。
- 確かめる対象は 4 つある。親のセッションが止まった開いている Epic、coordinator が通知を受けていない単独タスク、開いた Epic が無い開いているマイルストーン Issue、`backlog` の全件。候補を選ぶときは、README の目的と成功の条件も読む。閉じた Epic のコメントは読まない。残りは閉じる前に開いた Issue に移してあるから。
- GitHub の API の上限は、利用者の全リポジトリ・全エージェントで共有している。一覧では番号と題名などの軽い項目だけを取り、本文とコメントは候補の Issue だけ読む。Orca で分かること（セッションの生死や未読の通知）は、GitHub より先に手元の Orca で確かめる。一覧が件数の上限で切れていないかも確かめる。切れた古い Epic を、無いものと読まないため。
- 未読の通知や、開いている子が無いことは、調べるきっかけで、親が止まった証拠ではない。親のセッションが生きていれば、手を出さない。二重に起こすと、2 つの親が同じ Epic を進めるから。止まったと確かめられた親だけを立て直す。止まったと決められないときは、立て直さず、見つけたことを Epic にコメントし、返事で利用者に確かめる。
- 開いた Epic が無い開いているマイルストーン Issue は、次の着手待ちで、異常とは限らない。Epic を勝手に立てず、その sub-issue の `backlog` から候補を選び、おすすめと理由を付けて返す。成功の条件を満たしているなら、利用者に確かめてから閉じる。
- `backlog` は、番号と題名から候補を選び、候補だけ本文を読む。本文が指す事実がもう当てはまらないもの（再現しない・コードや設定が変わった・要望が無くなった・確かめたら起きていなかった）は、確かめた理由をコメントしてから閉じる。ほかの `backlog` は閉じない。
- 返事には、立て直したことと閉じたことを先に書き、そのあと次の着手の候補を、おすすめとその理由を付けて書く。

#### 窓口: 依頼を振り分ける
- 「〜したい」だけで着手の意思が分からなければ、最初は「今着手しますか」とだけ聞く。計画や技術の選択は、今やると決まってから考える。「〜して」と明確に頼まれたら、着手するかを聞き直さない。
- 今は着手しないと決まったら、利用者の言葉、分かっている事実や根拠、困る人を `backlog` の Issue に残し、URL を返す。同じ要望が既に `backlog` にあれば、新しい Issue を立てずにその Issue を使う。
- 着手するなら、大きさで層を選ぶ。作業時間が 4 時間以内で閉じるなら単独タスクにし、窓口が coordinator としてワーカーを起動する。4 時間を超え、利用者が使える変化が 1 つなら Epic にする。複数の Epic にまたがるなら、マイルストーン Issue を立てて利用者の言葉と成功の条件を利用者と合意し、成功の条件に向かう最小の変化を最初の Epic として sub-issue にする。残りの Epic の候補は、分かった時点でそのマイルストーン Issue の sub-issue の `backlog` の Issue にする。小さな単独の作業に Epic を強制しない。
- 着手が決まったのに、4 時間に収まるかが分からないときは、利用者に聞き直さず Epic にして親に渡す。大きさは調べないと分からないので、調べるのは親にする（4 時間以内と分かれば親が Task に書き換える）。
- Epic の本文には、困りごとと確認した事実だけを書き、すぐに Epic の親のセッションに渡す。目的・完了の状態・計画は、親が調べてから書く。窓口で計画まで立てると、調べる段階が省かれて計画が浅くなるから。
- Epic の親は、窓口が自分の Run から、Epic の worktree にワーカーとして起こす。親は自分で Epic の Run を作って、その coordinator になる。窓口が Epic の Run を作ると、親がその Run のワーカーになり、coordinator になれないから。窓口の Run から起こすのは、窓口が親の生死を Orca で確かめ、止まったときに立て直せるようにするため。親は利用者と直接話すので、ターンを終えてもセッションを残す。親が子や利用者の返事を待ってターンを終えたときに届く停止の知らせは、待っている合図なので対応しない。

#### 窓口: 単独タスクの coordinator を務める
- 何ができたら終わりかを Task Issue に書いてから、ワーカーを起動する。結果を左右する情報が依頼から分からないときだけ、起動前に一度にまとめて聞く。例えば README のリンク修正なら「README のリンクを開くと対象のガイドが表示される」と書けるので、確認を挟まずに任せる。
- 単独タスクごとに Orca の Run を作り、Run の id を Task Issue の本文に書く。窓口が GitHub を読まずに Issue と Run を対応づけ、窓口のセッションが替わっても通知を受け直せるようにするため。
- ワーカーの質問は、Issue と利用者の決定から答えられるなら、利用者に聞き直さずに答える。目的の変更や `hold-merge` の PR の承認のように、利用者にしか決められないことは、判断に要る中身・選択肢・おすすめをその場に書いて聞く。利用者の答えが決まるまで返事を送らない。
- 最小の 1 本に絞っても 4 時間に収まらないとワーカーが上げてきたら、単独タスクを Epic に引き継ぐ。新しい Issue は立てず、同じ Issue を Epic にする。元のワーカーには、実装を続けず Issue を閉じないことを伝え、済んだ範囲と元の Run の id を Issue にコメントしてから、Epic の親を起こす。分かった事実と利用者と合意済みの範囲を、そのまま親に引き継ぐため。
- `worker_done` が成功でも、それだけで完了としない。Task Issue が閉じて報告のコメントがあり、マージが要る PR がマージ済みであることを確かめる。通知は完了の合図で、完了の証拠は Issue と PR の状態にあるから。そろっていなければ、片付けず、続きを Task Issue にコメントしてからワーカーに送るか、利用者に伝える。失敗の通知なら、同じ Task を起動し直すか、新しい Task にするかを決める。
- 片付けたら、利用者ができるようになったことと、残りがあれば開いている Issue の URL を報告する。

#### Epic の親: 計画を立てる
- 渡された Epic には、困りごとと確認した事実だけがある。親は、リポジトリと既存の Issue を調べてから、目的・完了の状態・計画を書く。調べる前に書くと、計画が浅くなるから。
- 最初に Epic の Run を作り、Run の id を Epic の本文に書く。親が落ちたとき、立て直した親がこの Run を引き継いで続けるため。
- Epic の本文には、元の困りごとと事実を残したまま、完了の状態・利用者の流れ・計画（案）・外したものを書く。コメントに書くだけでは、子と次の親が本文から読めないから。
  - 完了の状態は、MVP までにし、ストーリーごとに観測できる確認項目を置く。
  - 利用者の流れは、利用者の操作や画面の順を Mermaid の flowchart で書く。
  - 計画は、子の作業の依存グラフを Mermaid で書く。ストーリーごとに、着手の前にそろっていなければならないもの（先行するストーリー・成果物・判断）を辺として描く。並行して進める組と着手の順序は、このグラフから決める。依存を書かずに順序や組だけを決めると、その組み方が正しいかを誰も確かめられず、依存のある子を並行で起動してしまうから。最初の子は、利用者の流れを 1 本だけ、最も短い形で、必要な層すべてに通すものにする。
  - 外したもの（拡張と対象外）は、`backlog` の Issue にしてリンクする。
- 技術の設計（データモデル・API・置き場所・ライブラリの選定）は、Epic の本文に書かない。最初の子が、作業の最初に決める。親が調べた範囲だけで決めた設計は、子の作業を縛り、子が実装で分かったことを反映できなくなるから。
- 書いた計画は、完了の状態の変化が 1 つか、最初の子が最小の 1 本か、各子が 4 時間に収まるか、同じファイルやインターフェースを触る子どうしに依存の線を引いたか、で見直す。例: 「会議を集めてナレッジグラフにし、Claude Code から使えるようにする」なら、最初の Epic の目的は「Claude Code から、自分の tl;dv の会議 1 件を検索できる」にする。
- 調べた結果、全体が 4 時間以内で閉じると分かったら、Epic のまま計画しない。Issue を単独タスク（type: Task）に書き換えて受け入れ条件を書き、親自身がその coordinator としてワーカーを起動する。窓口へ渡し直すと、窓口のセッションが動くまで作業が止まるから。親の worktree は、その Task が閉じた後に消す。
- 利用者に、目的・完了の状態・全体の流れ（利用者の流れと依存グラフ）への合意を求める。返事には、合意してほしい中身を本文で書き、Epic の URL を添える。名前・置き場所・実装の方針のような細部は聞かず、推しで決めて、選んだものと理由を返事に書く。合意をもらうまで、子の Issue を立てず、ワーカーを起動しない。

#### Epic の親: 子を起動する
- 起動するのは、依存グラフで先行が無いノードか、先行がすべて閉じているノードだけにする。先行が PR を伴う作業なら、その PR がマージ済みであることも確かめる。後続が必要とする変更が main に入っていないと、後続のワーカーが前提を作り直してしまうから。どの先行でも、閉じていることに加え、後続が必要とする成果（マージされた変更・調べた結果・反映された設定）が実際に使えることを確かめる。ワーカーは受け入れ条件を片付いた範囲に狭めて閉じることがあるので、閉じていても後続の前提がそろったとは限らないから。先行が閉じていないノードは、Issue も立てない。後で必要になった時点の状況で書くほうが正確だから。
- 既に子 Issue があるノードには、新しい Issue を立てない。ワーカーが生きている子を起動し直すと、2 つのセッションが同じ作業を進めるから。子 Issue があるのにワーカーが居ない子（起動の途中で止まったときなど）は、その Issue と、あれば既存の worktree を使って、同じ作業を起動し直す。
- 同じファイルやインターフェースを触るのに依存の線が無いノードがあれば、起動の前に Epic の本文のグラフへ線を足し、先行にしたほうだけを起動する。同時に動かすと、変更がぶつかるから。
- 並行して起動するのは、互いの未完了の作業を待たずに、それぞれの受け入れ条件まで進められる子だけにする。例えば、API の実装が必要な画面は API のマージ後に起動し、その API に依存しない別の作業は並行してよい。
- 依存関係は Epic の本文のグラフにだけ置き、Orca の Task には持たせない。計画を書き換えるたびに Task を作り直すことになるから。
- 子 Issue は Epic の sub-issue（type: Task）にし、受け入れ条件をストーリーごとに書く。ワーカーに渡す指示には、作業 Issue・報告先・作業時間の目安を書き、起動する前に同じ全文を子 Issue にコメントする。エージェントとモデルは、作業 Issue なら Opus か Sol の effort medium にし、ごく小さい修正だけなら Sonnet の effort medium か Sol の effort low にする（理由と選び方は「Issue を渡すエージェントとモデルは、作業の中心と使用量で選ぶ」の節にある）。
- Epic の目的と独立した作業（この Epic が無くても同じ作業が要るもの。例: CI の不具合・flaky なテスト・アカウントや上限の設定）は、今着手が要らなければ `backlog` の Issue にする。子の着手にその作業が要るときだけ、Epic の子として依存グラフに先行として描き、ほかの子と同じように起動する。別の Run や別の coordinator に分けると、親の立て直しや窓口の確認から漏れるから。

#### Epic の親: ワーカーの質問と停止に対応する
- Epic の計画と利用者が決めた内容から答えられる質問は、利用者に聞かずに答える。利用者を伝言役にしないため。答えは作業 Issue にコメントしてから、同じ全文をワーカーに返す。
- 利用者にしか決められない質問（目的や完了の状態に関わる選択、指示書の本文、`hold-merge` の PR のマージの承認）は、利用者に聞く。返事の本文に、判断に要る中身・選択肢・おすすめとその理由を書く。指示書の本文は、入れる本文の全文を見せて OK をもらう。方針に合意しても、文面が論点になることが多いから。利用者の答えが決まるまで、ワーカーに返事を送らず、完了の状態も書き換えない。
- 質問が新しい作業や方針の変更を含むときは、Epic の完了の状態に要るなら計画に足して確認項目に紐づけ、要らなければ `backlog` の Issue にする。
- `worker_done` を出さずに止まったワーカーの知らせは、放置しない。原因を作業 Issue のコメントから読み、続けさせる指示を作業 Issue にコメントしてから送る。続けられないと分かったら、利用者に伝える。

#### Epic の親: 報告を照合し、計画を見直す
- `worker_done` は完了の合図で、完了の証拠は Issue と PR の状態にある。子 Issue の報告（片付いたこと・片付かなかったこと・計画に影響する発見）を読み、子 Issue が閉じていること、マージが要る PR がマージ済みであることを照らす。食い違えば、片付けず、子 Issue にコメントして続けさせるか、利用者に伝える。
- 失敗の報告は、完了として扱わない。原因を読み、同じ作業を起動し直すか、新しい子を立てるかを、親が決める。利用者に聞くのは、目的や完了の状態に関わる選択だけにする。
- 照合が済んだら、子の worktree を片付ける（「セッションと worktree」の条件に従う）。
- 報告の「計画に影響する発見」と「片付かなかったこと」を読み、完了の状態の確認項目に紐づく作業は計画に足し、紐づかない作業は、子が既に `backlog` の Issue にしていなければ、`backlog` の Issue にする。残りのノードが今でも要るか、前提に合っているかも確かめ、要らなければ理由を Epic にコメントして計画から消し、ずれていれば書き換える。計画を書き換えたときは、依存グラフも同じ編集で直す。子が閉じた直後が、状況が一番新しく、見直すセッションの文脈も新しい時点だから。
- Epic に観測を 1 行コメントする（閉じた子、足したノード、経過したリードタイム）。子が閉じるたびに利用者には知らせない。判断が要る通知が埋もれるから。
- 完了の状態を満たしていれば、Epic を閉じる。満たしていなければ、先行がそろった次のノードを起動する。Epic の目的そのものが要らなくなっていたら、取り下げてよいかを利用者に聞く。

#### Epic の親: Epic を閉じる
- 完了の状態の各項目を、子の報告・PR・実際の動作と照らす。満たしていない項目がまだ今の子の大きさで片付けられるなら、子を起動する。
- 片付かなかったことと対象外の各項目に、`backlog` の Issue へのリンクがあるかを確かめ、リンクが無い項目だけを `backlog` の Issue にしてリンクする。既にリンクがある項目を立て直すと、同じ課題の Issue が二重になるから。Epic がマイルストーン Issue の sub-issue なら、その目標に向かう `backlog` の Issue を、マイルストーン Issue の sub-issue にする。`backlog` の本文には、子の報告にある解決の見込みを写さない。
- 完了の状態を満たしたら、completed で閉じる。大きすぎると分かったときは、外す部分を先に `backlog` の Issue にし、完了の状態を満たした範囲まで狭めて Epic の本文に書き、completed で閉じる。狭めてよいのは、満たした範囲に利用者が最初から最後まで使える変化があるときだけにする。無ければ狭めずに計画を立て直すか、利用者に確かめて取り下げる。使える変化の無い Epic を completed で閉じると、何もできるようになっていないのに完了と読まれるから。閉じるコメントの冒頭に「分割」と書き、外した部分の Issue を参照する。取り下げは、利用者が言い出したときも、取り下げるリスク（無駄になる作業や未マージの PR、中途半端に残るもの）、やり残し（残りの項目と移す先の `backlog`）、後片付け（子 Issue・ワーカー・worktree・PR をどうするか）を示して確かめてから、not planned で閉じる。「もう要らない」は意向で、失うものを知ったうえでの了承ではないから。
- 利用者には、何をできるようになったかと、残りをどの `backlog` の Issue に置いたか（URL）を伝える。親の worktree を残したなら、その理由も伝える。

#### Epic の親を立て直す
- 窓口は、親が止まったと確かめられた Epic だけを立て直す。先に Epic に、立て直すことと理由をコメントする。新しい親が Issue から続けられるようにするため。新しい親は、窓口が自分の Run から、既存の Epic の worktree に起こす。窓口が Epic の Run を束ねると、子の質問が窓口に届き、新しい親がその Run を引き継げなくなるから。
- 立て直された親は、Epic の本文にある Run を引き継ぎ、状態を組み立ててから動く。前の親が残した状態は、Epic の本文・コメントと子 Issue と、Orca のワーカーの状態と通知にある。GitHub の API の上限は共有なので、手元の Orca を先に読み、コメントは必要な子だけ読む。
- ワーカーが生きている子には、何も起動しない。新しく起動すると、2 つのセッションが同じ作業を進めるから。答えの無い質問がある子には、答えを子 Issue にコメントしてから、元のワーカーに続けさせる。送れなかったときだけ、同じ作業を既存の worktree で起動し直す。利用者にしか決められない質問は、利用者の答えが記録されていなければ、利用者に聞いてから続けさせる。閉じている子は、照合に入る。
- 状態を確かめたことと、何を起動した（しなかった）かを、Epic にコメントする。Epic の本文に Run の id も計画も無ければ、前の親は計画を書く前に止まっているので、計画を立てるところから始める。

#### ワーカー: 作業を進める
- 作業 Issue は、工程（調査・設計・実装・テスト）で割らず、ストーリーで割る。1 つの作業 Issue のセッションが、そのストーリーの調査・設計・実装・テストから PR のマージまでを通して行う。工程ごとに別の Issue やセッションに分けると、引き継ぎのたびに文脈が落ち、前の工程で下した判断の理由が後の工程に届かないから。例: 「設計の子」「実装の子」「テストの子」を立てず、「〜として〜できる」の子を 1 本立てる。エージェントやスキルの評価データセットを作る作業は、テストの工程ではなく、測定の道具を作る別のストーリーとして扱う。評価データセットは、評価されるエージェントやスキルを作るセッションに見せない。作る側が見ると、評価データセットに合わせて作ってしまい、測った数字が別のデータでは再現しないから。
- ワーカーは、設計・実装・テストを自分で進める。同じ作業の段階どうしは文脈を多く共有するので、別のエージェントに分けると引き継ぎで文脈が落ち、調整の手間が増えるから。別のエージェントに分けてよいのは、次の 2 つにする。
  - 仕上げのレビューを、実装したモデルと別の会社のモデルに依頼する。
  - 読むファイルが多く、結論だけ持ち帰ればよい調べものを、セッション内のサブエージェントに依頼する。読んだ中身で自分の文脈を埋めないため。

  どちらにもファイルを書き換えさせない。レビューは指定したツールの標準手順に従い、内部のレビュー用サブエージェントを使ってよい。調べもののサブエージェントには、さらにエージェントを立てさせない。並行させたい実装は、Epic の計画で独立した子に分ける。
- 範囲外の作業に着手せず、作業 Issue の子を立てない。今の Issue に作業を足し続けると、4 時間で閉じられなくなるから。見つけた課題が Epic の完了に要るなら、見つけた時点で作業 Issue にコメントし、`ask` で親に戻す。`worker_done` の報告に書くだけでは、親が計画に入れる契機にならないから。要らない課題と、単独タスクの残りは、`backlog` の Issue にする。
- 着手した後に未解決の依存が見つかったら、作業 Issue にコメントしてから `ask` で coordinator に戻し、ターンを終える。依存の解消を待つのは coordinator の計画で、ワーカーが待ち続けると作業時間だけが延びるから。
- 単独タスクで、最小の 1 本に絞っても作業時間が目安に収まらないと分かったら、Issue を閉じず、済んだ範囲と見積もりを作業 Issue にコメントし、同じ全文を `ask` で窓口に送って、Epic に引き継ぐかの判断を待つ。それ以外で作業時間が目安を超えそうになったら、延ばさない。受け入れ条件を片付いた範囲に書き換えて閉じ、外した範囲は上の課題と同じように置く。マージしていない層は draft のまま残し、PR の本文に引き継ぐ先を書く。

#### ワーカー: 閉じる
- ワーカーは、マージ、作業 Issue への報告（片付いたこと・片付かなかったこと・計画に影響する発見）、Issue を閉じる、`worker_done` を送る、の順で終える。coordinator は通知を受けて報告と状態を照らすので、通知の時点で報告とマージが済んでいる必要があるから。
- 作業 Issue か PR に `hold-merge` が付いていれば、coordinator から承認の返事を受けるまでマージしない。承認を求める内容を作業 Issue にコメントしてから、`ask` で coordinator に上げる。
- 完了した範囲を示せなければ、Issue を開いたままにし、理由を報告して、失敗として `worker_done` を送る。失敗を成功として送ると、coordinator が完了と取り違えて片付けてしまうから。
- worktree は、`worker_done` を受けた coordinator が片付ける。ワーカーは自分の worktree を消さない。

<!--skill-->窓口と Epic の親の手順（確かめ方・Issue の立て方・Orca での渡し方・閉じ方）は、スキル `issue-planning` にある。窓口は、次の着手を決める前と、依頼を Issue にする前に読む。Epic の親は、渡された指示に従い、スキルの入口にある「Epic の親が読む節」から場面に合った参照を読む。ワーカーはスキルを読まず、渡された指示とこの節に従う。<!--/skill-->

### PR は小さく割ってスタックで積み、条件がそろった層から入れる
- PR は実測で割る。作業の途中で `git diff --stat` を見て、手で書いた変更行が 400 行を超えたら、CI が通る位置で区切る。区切った PR は GitHub のスタックド PR（`gh stack`）で積み、下の PR のマージを待たずに上の層の作業を続ける。削除だけの行・生成物（lock ファイル・dist など）・機械的な置換（リネーム・一括整形）は数えない。400 行に届かなくても、互いに関係ない変更が混ざっていたら層を分ける。1 つの Issue から出すのは 1 つのスタックだけにする。スタックの層の数に決まりは無い。スタックは 1 つの流れとして `gh stack` で管理できるから。大きい変更ほどレビューで欠陥を見逃すことは、Mozilla の分析（Kononenko 2015）と統制実験（Baum 2019）で同じ向きに出ている。変更するファイルが多いほど、役に立つレビューコメントの割合が下がることも分かっている（Bosu 2015）。AI エージェントの PR でも、大きいものほどマージされにくい（Ehsani 2026。効果は小〜中で、CI の失敗のほうが強く効いていた）。一方で 400 行という線は、SmartBear が Cisco の 1 グループのデータから出した推奨（200 行未満が望ましく、400 行が上限）で、ほかの研究では確かめられていない。だから上限の目安として使い、小さく出せるなら小さく出す
- スタックの各層は、CI が通り、その層までをマージしても既存の動きを壊さない単位にする。Issue のストーリーは、各層ではなくスタック全体で片付ける。API だけ・画面だけの層は、それだけでは誰も使わない変更になるから。層は依存の順に積み、下に土台（データモデルなど）を置く。マージは、層ごとに次の 2 つがそろったら、確認を挟まずに下から順に 1 層ずつ `gh stack merge <PR 番号>` で行い、マージしたことを報告する。1 つは CI が通っていること、もう 1 つは仕上げのレビューに P0/P1 の指摘が残っていないことだ。main に入った変更は revert で戻せるので、そろった層を毎回止めると、待つ時間だけが増えるから。利用者が中身を見てから入れたい PR は、Issue か PR に `hold-merge` ラベルを付けておく。このラベルがある層は、マージの前に確認する。自動マージは使わない。条件を確かめた時点と、マージされる時点がずれるから。マージしたら `gh stack sync` で残りの層を main に rebase する。main を Restrict updates で守っていて `gh stack merge` が「Cannot update this protected ref」で止まるリポジトリでは、`gh api --method PUT repos/<owner>/<repo>/pulls/<番号>/merge-async -f merge_method=squash -f sha=<head の SHA> -F bypass_rules=true` で一番下の層を入れる。GitHub は bypass でのマージを一番下の PR にしか許さないので、下から 1 層ずつ入れる
- 作業用ブランチでは、commit・push・PR の作成と ready 化を、そのつど確認せずに進める。確認を挟むと作業が止まり、毎回同じ承認を求めることになるから。force push・履歴の書き換え・削除は戻しにくいので、先に確認する（マージと worktree の片付けは、それぞれの条件に従う）。自分のスタックの作業用ブランチを rebase して `gh stack push`・`gh stack sync` で再 push するのは、中身は force push だが確認せずに進める。スタックでは下の層を直すたびに上の層の rebase が要り、毎回止めると積む意味がなくなるから
- 1 つのスタックで `gh stack` を打つのは、同時には 1 セッション（持ち主）だけにする。`gh stack sync`・`gh stack push` は fetch した直後のリモートを基準に force push するので、別のセッションが同じブランチへ push したコミットを警告なしで上書きする。

### 調べてから組み、測り方は先に決める
- 確立した分野（統計・機械学習・アノテーション・セキュリティなど）にあたる作業は、着手する前にその分野の定石を調べる。手順は出典（論文・教科書・公的なガイドライン）付きで示してから進める。自己流で組んだ手順には、その分野が既に潰した誤りが残っている
- 何かの良し悪しを測る仕組み（スキルやプロンプトの評価、判定器、ベンチマークなど）を作るときは、指標・合格線・判定基準を、データや結果を見る前に決めて利用者と合意する。外れたケースに合わせて基準を後から直すと、基準が手元のデータに寄ってしまい、測った数字が別のデータでは再現しない。基準を直す必要が出たら、直した基準で全ケースを測り直し、それより前の数字とは比べない
- 変更の効果を数字で報告するとき（評価の通過率・所要時間・トークン数など）は、同じ条件で繰り返したときのばらつきの幅も測り、差と並べて示す。LLM の出力は同じ入力でも毎回変わるので、1回ずつ比べただけでは、効果とばらつきを見分けられない。ばらつきより小さい差は「改善」と書かず、「差は見えなかった」と書く

### AI エージェントは、判断をモデルに任せ、ハーネスには能力・境界・検証・状態を置く

この節は、AI エージェントを設計・実装・改修するときに適用する。ハーネスは、モデルを囲んで動かすプログラム（エージェントのループ・道具・権限・コンテキストの管理）を指す。

- 作る前に、最も単純な形で足りないかを確かめる。1 回の LLM 呼び出しで足りるならそれにする。入力と処理が定まる部分はコードやワークフロー（決めたコードの道筋で LLM と道具を呼ぶもの）にし、途中の結果を見て解き方を選ぶ部分はエージェント（モデルが自分で手順と道具の使い方を決めるもの）としてモデルに任せる。両方を組み合わせてよいが、どの判断をコードが持ち、どの判断をモデルに任せるかは意図して選ぶ。不要な制御でモデルの判断を狭めないため
- ハーネスには次の 4 つを置く。モデルは、その境界の中で、次に何をするか・どの道具を使うか・いつ終えるかを判断する
  - 能力: 情報を読み、環境へ作用するための道具。説明・引数・返り値・エラーメッセージを人向けの UI と同じ手間で作り込み、テストする。引数は間違えにくくする（例: 作業ディレクトリの取り違えが起きる道具では、絶対パスを必須にする）
  - 境界: 権限・サンドボックス・停止条件（ターン数・トークンの上限）・人の承認が要る操作。守る必要のある制約は、モデルの判断やプロンプトだけに頼らず、権限設定や実行前の検査で強制する
  - 検証: テスト・lint・型・スクリーンショット・受け入れ条件など、モデルが環境から結果を得て、自分の成果を確かめる手段。完了は、モデルの自己申告でなく成果物と検証結果で判定する
  - 状態: 作るエージェントが実行中に持つ計画・進捗・成果物を、セッションを跨いでも読める保存先に書き出す仕組み。人が計画を確認でき、次のセッションも引き継げるようにする。この開発作業の計画・進捗を置く Issue と、作るエージェントの状態の保存先は分けて設計する。コンテキストの圧縮もここに入る
- 操作を正確に実行することと、その操作をいつ選ぶかを決めることは分ける。例えば、返金ツールが二重返金を防ぎ、会計記録まで更新する内部手順はコードで決めてよい。その依頼を返金で解決するかは、要件と状況からモデルが判断する。「本人確認をしてから返金する」のように業務上必要な順序は、境界として強制する
- エージェントが失敗したら、その場で正解だった手順を分岐・専用ツール・スキルに足す前に、何を知らなかったか、何ができなかったか、何を確かめられなかったかを調べる。欠けていた情報・能力・フィードバックを補い、既知の失敗を固定手順へ置き換え続けない。例えば、テスト失敗に「必ず依存を再インストールする」という手順を結び付けるのでなく、失敗したテスト・エラー・実行環境をモデルが調べられるようにする
- ドメイン知識は、モデルが必要なときに読めるドキュメントやスキルに置く。ただし、コードからファイルへ移すだけでは、固定手順が増える問題は解決しない。指示には目的・制約・判断に必要な知識と代表例を書き、失敗するたびに「この場合は必ずこの順で動く」という例外を積み重ねない
- 評価が上がっただけでは、モデルの判断を固定する理由にしない。能力不足を補う制御を足すなら、モデルが自力でできないと仮定していることと、制御が無いと落ちる評価ケースを、コードや設定の隣に書く。修正に使っていないケースと、同じ兆候でも別の対処が正しいケースで、ほかの正しい解き方を妨げないか確かめる。どちらも修正に使ったなら、未知のケースでも通じた証拠とは扱わない
- 評価では、決めた道筋を再現したかでなく、要件を満たしたかを採点する。道具を呼ぶ順序を見るのは、その順序自体が業務上の要件である場合にする。正しい別解を落とす評価は、固定手順を増やす原因になるから
- モデルの能力不足を補う部品や指示は、モデル更新時に、外しても要件を満たすかを確かめ、不要になったら外す。モデルの限界についての仮定は、モデルが変われば古くなるから。権限・承認・停止条件など、モデルの能力と関係なく必要な境界は、この削除の対象にしない

### Issue を渡すエージェントとモデルは、作業の中心と使用量で選ぶ
親・子・単独の Issue を新しいセッションに渡すとき、そのセッションの役割で、エージェントとモデルと effort を 1 つ選ぶ。1 つの Issue の中で設計・実装・テストを別のモデルに分けない。同じ作業の文脈を共有したまま進め、引き継ぎを増やさないため。仕上げのレビューは別の会社のモデルに依頼する。
- モデルは、Claude の Opus か OpenAI の Sol のうち、サブスクの使用量に余裕がある方にし、役割の違いは effort で付ける。Epic の親のセッションは effort high、作業 Issue（子・単独）のセッションは effort medium にする。Anthropic は大半の作業を Opus から始めるよう勧めていて、その既定の effort が medium であり、high は複雑な推論向けとされている（[Models overview](https://platform.claude.com/docs/en/models/overview)・[Effort](https://platform.claude.com/docs/en/build-with-claude/effort)）。OpenAI は Sol を日常の作業の主力とし、コーディングで Astra に近い性能を約 5 分の 1 の費用で出すとしている（[GPT-6.2 Astra and Sol](https://openai.com/index/introducing-gpt-6-2-astra-sol)）。作業 Issue は設計からテストまでを 1 つのセッションで通すので、工程でモデルを分けない
- ごく小さい修正（lint の指摘直し・typo・リネーム・設定値の変更のように、判断がほとんど要らず数行で済むもの）だけの作業 Issue は、Claude の Sonnet を effort medium にしたものか、OpenAI の Sol を effort low にしたもののうち、使用量に余裕がある方にする。Sonnet は仕様が決まったエージェント的なコーディングを medium から始めるよう勧められていて、Sol は Sonnet と同じ価格帯なので low で足りる
- Fable と Astra は、利用者がそのセッションや作業に使うと指定したときだけ使う。Epic の親のセッション・レビュー・複数のモデルによる議論・サブエージェントの既定にはしない。どちらも Opus の 2 倍、Sol と Sonnet の 4 倍の単価で、長く続くセッションや並行する多数のセッションで使うと、数時間でサブスクの枠を使い切るから
- Orca で起動するときは、選んだモデル ID を `--model` で、effort を `--effort` で渡す
- 仕上げのレビューは、実装したモデルと別の会社のモデルにする（Claude が書いたら `codex review`、Codex が書いたら Claude の `/code-review`）。同じ系統のモデルは同じところを見落としやすいから。どちらのモデルが実装しても、欠陥はここで拾う
- モデルは系列名（Opus・Sonnet・Sol。Fable と Astra は利用者が指定したときだけ）で選び、その系列の最新世代を使う。前の世代は使わない。Claude は [Anthropic のモデル一覧](https://platform.claude.com/docs/en/models/overview) で、OpenAI は `~/.codex/models_cache.json` のうち `visibility` が `list` のモデルの `slug` で、選んだ系列の最新世代のモデル ID を確かめる。Orca で新しいセッションを起動するときは、その ID を `--model` で渡す。指示書に版の番号を書くと、新しい世代が出るたびに前の世代を選び続けるから
- モデルを選ぶたびに `agent-usage` を実行し、Claude と Codex の週間枠・5時間枠の使用率、リセット日時、最終取得日時を取り直す。前回の出力は使い回さない。実行し直しても取得日時が古い・枠が取得不可の場合は、その側のセッションで応答後に再取得する。それでも確認できなければ、不明な枠と選択理由を利用者に伝える。
- 作業に適したモデルのうち、作業を続けられる余裕があり、リセットまでに枠を余らせそうな側を優先する。使用率が高くても、枠が尽きても、リセットを待って作業を止めない。枠が尽きれば自動で従量課金に切り替わり、作業はそのまま続けられるから。片方の枠が尽きたらもう片方の会社のモデルへ切り替え、両方の枠が尽きたら従量課金のまま続ける。使用量は、どのモデルを選ぶかを決める材料にだけ使い、作業を止めるか・待つかを決める材料にはしない。
- レビューの P0/P1 の指摘が片方のモデルにだけ目立って多いときは、使用量で振るのをやめて利用者に伝える

### 対話の操作が要る確認も、エージェントが自分で行う
TUI のスラッシュコマンド（Codex の `/hooks` など）や信頼のダイアログのように、対話の操作が要る確認も、エージェントが Orca の端末で CLI を起動して自分で操作し、結果を確かめる（`orca terminal create --command <CLI>` で起動し、`orca terminal send` で入力して、`orca terminal read --screen` で画面を読む）。利用者に回すのは、ログインや 2 要素認証のように、エージェントが代われない操作だけにする。「対話の操作なので未実施」と利用者に回すと、作業がそこで止まり、確認が漏れたまま完了として扱われるから。
