# デプロイとリリース

main は常にデプロイできる状態を保つ。利用者へまだ見せない変更は、feature flag などで、利用者から見えない状態にしてから main へマージする。未完成の変更を長期間の feature branch に残すと、main との統合が遅れて差分が大きくなるからである。

main へのマージは stg へ自動でデプロイし、stg 専用の長期間の branch は作らない。stg で確かめたコミットと、リリース対象に選ぶ main のコミットを一致させるためである。

stg へのデプロイが失敗した場合は、main がデプロイできない状態として扱う。原因を main で直し、main の最新コミットのデプロイが成功したことを確かめる。stg だけを手作業で変更すると、次の自動デプロイで再現できない状態が残るため、失敗を手作業の変更で迂回しない。

本番へリリースするタグは、stg へのデプロイが成功した main のコミットを選び、`vMAJOR.MINOR.PATCH` の形で付ける。stg のデプロイは、待機中の実行が新しい実行に置き換わることがあり、main にあるコミットでも stg に上がっていないことがあるからである。stg へのデプロイが成功していないコミットにタグを付けると、本番のデプロイは始まる前に止まる。

タグを付ける前に、対象のコミットで CI と stg の deployment が成功し、変更した利用者の流れと、その変更が影響する既存の主要な利用者の流れを stg で完了できることを確かめる。例えば、注文を変更した場合は、変更した注文の流れに加えて、既存の注文を作成して完了する流れも確かめる。リポジトリにリリース固有の確認項目がある場合は、それも同じコミットで確かめる。

版は Semantic Versioning に従う。互換性を壊す変更では MAJOR、互換性を保った機能追加では MINOR、互換性を保った修正では PATCH を上げ、上げた桁より右の桁を 0 に戻す。まだ安定版として公開していない `0.y.z` では、互換性を壊す変更で MINOR、互換性を保った機能追加と修正で PATCH を上げる。版を変更内容ではなく作業量で決めると、利用者が更新の影響を版から判断できないからである。

本番の問題を検知した場合は、影響が続くことによる損失と復旧方法の安全性を比べて、前のタグへ戻すか、main で直して次のタグを付けるかを決める。前の版が現在のデータ・データベース schema・外部サービスと互換で、戻すほうが利用者への影響を早く止められる場合は、前のタグを指定して再デプロイする。後方互換性のないデータ変更や外部への副作用があり、前の版へ戻すとデータを壊す場合は戻さず、main で修正し、そのコミットを stg で確かめて新しい PATCH のタグを付ける。リリース済みのタグを別のコミットへ動かすと、同じ版が異なる内容を指すため、タグは更新せず、新しい版を付ける。
