# 成果物種別

「何を作っているか」の分類。[test-strategy.md](./test-strategy.md) の各詳細テスト戦略と、`setup` が成果物種別を特定する箇所は、この分類を参照する。分類そのものはこのファイルを正本にし、ほかのファイルには複製しない。複製すると、片方だけが直されて分類が食い違うから。

## 分類軸

主軸は**インターフェース種別**（外部と何を通じてやり取りするか）の1本にする。実行モデル・検証モデル・詳細戦略の有無は、軸にせず、各行の属性列にする。3つの軸を掛け合わせると、存在しない組み合わせまで行が増えるから。

- **実行モデル**: 常駐（リクエスト/操作待ち）・クライアント常駐（ユーザー操作待ち）・バッチ（都度またはスケジュール起動）・イベント駆動（メッセージ待ち）・宣言的適用（reconcile）・呼び出し元に従属（ライブラリ/SDK。自身は実行環境を持たない）・なし（ビルド成果物）のいずれか、または対象がどちらの起動もあり得る場合はこれらの組み合わせ（`X/Y`表記）
- **検証モデル**: 3層（[test-strategy.md](./test-strategy.md)のunit/integration/acceptance）・unit/integrationのみ（受け入れは呼び出し側か integration で確かめる）・スタック固有段階（同「インフラ成果物種別テスト戦略」、acceptance層を置かない）・静的検証のみ・プロジェクトの AC で定める
- **詳細戦略**: 有（test-strategy.mdに専用節がある）・無（分類上は存在するが専用節は無い。追加は下記「詳細戦略が無い型の扱い」に従う）

複数の型にまたがる対象（例: UI操作の結果として、APIのエラーレスポンスも主張している）は、主たる入口を1つ選び、ほかの型が求める観測点を別に併記する。入口を1つに決めないと、どの型の戦略でテストするかが決まらないから。

そのとき、無理に1つの型へ押し込めて、もう一方の型の観測点を捨てない。捨てた観測点は、誰も確かめないまま残るから。

新しい種別は、既存の13型に実際に収まらなかった具体的な依頼が出たときだけ足す（以下、これを種別を増やす条件と呼ぶ）。依頼の無い種別を先に足すと、使われない分類と戦略が増え、どの型に当たるかを選ぶ手間だけが増えるから。

## 詳細戦略が無い型の扱い

「詳細戦略」列が無の型に当たったら、次のように判断する。

- 分類一覧の実行モデル・検証モデルを手がかりにし、AC自身（またはテスト対象自身）が観測点を名指ししていれば、審査・実装を続ける。観測点が決まっていれば、詳細戦略が無くても何を確かめるかが分かるから。
- 観測点を名指しできない対象は、詳細戦略が無いことを理由に無条件で通さず、書き直しを求める。通すと、何を確かめたのかを誰も説明できないテストが残るから。
- 詳細な戦略表（unit/integration/acceptanceで何を見るかの表）は、種別を増やす条件と同じく、実際にその型で具体的な依頼が出た時点で [test-strategy.md](./test-strategy.md) へ節として足す。依頼の無い型の戦略表は、使われないまま古くなるから。
