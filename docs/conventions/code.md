# スタックに共通のコーディング規約

言語に関係なく、コードを書く・レビューするときに守る決まり。スタック別の決まりは、同じディレクトリのスタックの規約（`typescript.md` など）にある。

## コメントと型

- 足したり変えたりしたコメント・docstring・文書は、実装と同じことを言うようにする。食い違ったコメントは、無いより悪く、読み手を誤った前提で動かすから。
- 型は、ありえない状態を表せないように作る。例えば、状態が「完了」なのに完了日時が空、という組み合わせを作れる形（互いに決まり合う欄を別々の欄で持つ形）にしない。表せる状態は、いつか必ず作られるから。

## 例外の扱い

- 例外を捕まえて別の値や処理に切り替える（フォールバックする）箇所には、なぜそうしてよいかをコメントに書く。理由の無いフォールバックは、本来知らせるべき失敗を隠すから。
- 判定できない状態を「無し」「成功」「確定」として扱わない。例えば、取得に失敗した一覧を空の一覧として返さず、取得できなかったことを呼ぶ側へ伝える。分からない状態を正常な値に替えると、呼ぶ側が誤った前提で処理を進めるから。根拠はhelix・helix-saasのレビュー約10件と、kiogiwaraの17 PR（[#59の調査](https://github.com/spikestudio/engineering-standards/issues/59#issuecomment-6908328808)）。

## CLI・バッチの結果と後始末

結果を書くCLI・バッチは、途中で止まってもやり直せるようにする。途中の結果を完成した結果として使ったり、再実行で前回の結果を失ったりしないため。根拠はkiogiwaraの38 PRと、helix-saasのレビュー6件（[#59の調査](https://github.com/spikestudio/engineering-standards/issues/59#issuecomment-6908328808)）。

- ファイルの結果は、出力先と同じディレクトリに作った一時ファイルに書き、書き終わってから名前を変えて公開する。別のファイルシステムへのコピーに替わることを避け、書きかけのファイルを完成した結果として読ませないため。
- 前回の結果を、利用者が気づかないうちに上書きしない。例えば、出力先が既にあれば失敗にし、置き換える場合は利用者が明示したときだけにする。やり直しで有効な結果を失わないため。
- 失敗したら0以外の終了コードで終わる。呼ぶ側のスクリプトに成功と判断させないため。
- 接続・子プロセス・ロックは、正常終了でも失敗でも確実に解放する。例えば、例外でも通る`finally`やコンテキストマネージャーで後始末する。残った接続やロックで再実行を妨げないため。

## 同じ値の正本

同じ値は1か所で定義して共有する。importできない値は共有のパッケージに切り出す。文書は生成できるものはすべて生成する。2か所に持って突き合わせのテストで守る形にはしない。例えば、APIのエラー定義を実装で共有し、その定義からOpenAPIを生成する。片方だけが更新されるずれと、同じ変更を何度も行う手間を無くすため。根拠はhelix・helix-saasのレビュー約10件（[#59の調査](https://github.com/spikestudio/engineering-standards/issues/59#issuecomment-6908328808)）。

## 構文のある入力

TOML・JSONC・YAML・シェルの引数・版の指定は、正規表現で読まず、既製のパーサを使う。例えば、TOMLの値はコメントや引用符を自前で取り除かず、TOMLパーサで読む。引用符・エスケープ・入れ子などを取りこぼし、正しい入力を誤って読むことを防ぐため。根拠はhelixのレビュー約9件（[#59の調査](https://github.com/spikestudio/engineering-standards/issues/59#issuecomment-6908328808)）。

## 利用者が渡すURL・経路

利用者が渡すURLやURLの経路は、URLとして解釈した後の値で判定する。生の文字列の前方一致などで許可しない。例えば、`https://allowed.example@evil.example/`のホストは`evil.example`なので、`allowed.example`へのURLとして許可しない。検証と実際のアクセスで解釈がずれると、許可していない宛先や経路に到達するから。攻撃の入力を並べたunitテストで、拒否できることを確かめる。根拠はhelix-saasのレビュー4件（[#59の調査](https://github.com/spikestudio/engineering-standards/issues/59#issuecomment-6908328808)）。

## API

- 実装が返すエラーは、すべて OpenAPI にも書く。書いていないエラーは、呼ぶ側が扱いを用意できないから。エラーの形と HTTP ステータスの対応は [test-strategy.md](./test-strategy.md) の「REST API」にある。
