# データベース規約

DB を使うプロジェクトで、選定・読み書き・変更時に守る決まり。DB ツールの選定は、導入した言語の規約に従う。

## 選定

既定は PostgreSQL とする。ほかの DB を選ぶときは、その DB が必要な理由をプロジェクトに残す。

## 排他

読んでから書く処理は、同じトランザクションでの行ロックか DB の制約で守る。同時に呼ぶ integration テストで、更新の取りこぼしや重複が起きないことを確かめる。アプリ内で順番に呼んだだけでは、別プロセスからの同時更新を防げないから。

## マイグレーション

制約を足す前に、既存の行がその制約を満たすか検査する。マイグレーションは 1 つのトランザクションで適用し、途中の失敗で一部だけが残らないようにする。トランザクションで実行できない操作は別の変更に分け、失敗時の復旧手順を用意する。デプロイ中に旧版と新版のコードが並んでも読み書きできることを integration テストで確かめる。

## 読み書きの経路

1 つの DB に読み書きするのは、その DB を持つ 1 つのアプリだけにする。seed・取り込み・管理用 CLI も、そのアプリのドメイン層（業務の検証と処理を持つ層）を通して書く。値の形の検証はアプリで持ち、DB には一意制約や外部キーなど、同時更新でも整合性を守る制約を置く。別の経路で値を書かないことで、検証のずれを防ぐ。

本番の DB を手で直したときは、同じ変更をマイグレーションや修復用コードとして残す。手元や次の環境でも再現できるようにするため。

## import の境界

TypeScript・Python のデータアクセス層は `src/data/` とし、DB ツールの import はここにまとめる。検査は、CLI・seed・テストを含むプロジェクト全体（pnpm workspace では各パッケージの全体）を対象にする。別の構成では `.dependency-cruiser.cjs`・`ruff-data-layer.toml` の境界を理由付きで変更する。層を飛ばした import は `check:deps` が止める。

Python の Alembic 環境は `uv run alembic init src/data/migrations` でデータアクセス層内に作る。既存の環境を移すときは、`env.py` と `versions/` を含むディレクトリを移し、`alembic.ini` の `script_location` も移動先に合わせる。

ドライバを直接 import せず、言語の規約で選んだ DB ツールを使う。接続にドライバが必要な 1 本だけ、`src/data/connection.ts`・`src/data/connection.py` を ESLint・Ruff の設定で例外にしている。場所を変えるときは、元の例外を残さず、設定のパスと理由を変更する。
