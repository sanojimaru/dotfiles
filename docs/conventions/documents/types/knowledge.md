# 知識・計画・記録

出典: [iwasa-kosui/tanteki](https://github.com/iwasa-kosui/tanteki) bcf2b1dのreferences/types/knowledge.md（MIT、[NOTICE](../NOTICE.md)）。

開発の計画・進捗を管理する場所と、決定の経緯の残し方は [accuracy.md](../accuracy.md#作業の状態と決定の経緯を分ける) に従う。以下は文書や Issue 本文、報告の役割を説明するもので、別の管理先を増やすための一覧ではない。

## プロジェクト計画

PM（プロジェクトマネージャー）、開発、関係部署に向けた計画書である。成果物、担当、節目、先に必要な作業・条件、リスクを調整する。要求や設計の根拠を保存する文書ではない。区分は `flow` とする。

誰がどの成果物を担当し、どの節目までに何を進めるかを示す。着手や完了に先立って必要な作業・条件と、計画に影響するリスクを説明する。判断が必要になる時期や条件も示し、関係者が調整できるようにする。

## 進捗/status report

チーム、管理者、関連する作業の担当者に向けた進捗報告である。現在の状況、前回からの変化、作業を妨げている要因、判断してほしい事項を伝える。仕様・設計・決定の正式な参照先にはしない。区分は `flow` とする。

報告の対象期間に完了したことと、次に行う作業を区別する。阻害要因は影響する作業に結び付け、判断依頼は誰に何を決めてほしいかを示す。追跡先の課題やPRを参照してよい。

## 技術調査の報告（Spike）

開発者、PdM（プロダクトマネージャー）、意思決定者に向けた技術調査の記録である。不確実性を減らすために調べたこと、選択肢、限界を残す。意思決定や実装の進捗管理の代わりにはしない。区分は `record` とする。

どの疑問をどの方法で調べ、何が分かったかを説明する。調べた条件による限界を示し、その範囲で選択肢を評価して提案する。現在の設計とその理由は Design Doc、決定に至る経緯はコミットや PR、作業の進捗は Issue に残す。

## 会議メモ

参加者、欠席者、関係者に向けた会議の記録である。扱った論点と確認した事実を後から確認できるようにする。正式仕様や作業管理の代替にはしない。区分は `record` とする。

いつ誰が参加した会議かを示し、論点と確認した事実を対応させる。現在有効な決定と、それを理解・適用する理由は、対応する仕様書・設計書などの `stock` に残す。決定の経緯はコミットや PR を参照し、次の作業の担当・期限は Issue で管理する。

## README

利用者、開発者、保守者に向けたリポジトリやサービスの案内である。入口と次の行動を示す。完全なAPI仕様や設計書を複製する文書ではない。区分は `stock` とする。

何のリポジトリやサービスかを説明し、使い始める手順と、詳細を確認する主要なリンクを示す。保守者も明記し、問い合わせ先を分かるようにする。

## チュートリアル

初学者や利用者に向けた導入手順である。最小の成功体験へ導く。全機能のリファレンスにはしない。区分は `stock` とする。

前提を満たした読者が手順を実行し、期待結果を確認して次のリンクへ進めるようにする。

## 操作/利用ガイド

利用者、CS（カスタマーサポート）、運用担当に向けた操作手順である。よくある目的を安全に達成する方法を示す。内部実装や開発進捗は説明しない。区分は `stock` とする。

対象と前提を定め、手順と得られる結果を対応させる。操作の条件や失敗を避けるための注意を添え、解決できない場合の問い合わせ先を示す。

## FAQ/トラブルシュート

利用者、CS、オンコール担当に向けた問題解決案内である。症状から確認・解決までを短くたどれるようにする。根本原因の正式な記録や、個別の障害の経過を記録する文書としては使わない。区分は `stock` とする。

症状と起きる条件を対応させ、確認から解決へ進めるようにする。自分で解決できない場合の相談先と連絡方法を残す。

## 確認依頼

確認を依頼するときは、相手に同意してほしい内容を文で示す。観点を並べるだけでなく、何に同意するか、何を修正してほしいかを返せる形にする。
