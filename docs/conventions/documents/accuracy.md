# 記述の正確さと情報の保存先

文書を実態と合わせ、前提・用語を明確にし、作業の状態や決定の経緯と分けて保つための決まり。このファイルは engineering-standards で書いたもので、[NOTICE](NOTICE.md) の取り込み元を持たない。

## 読者の判断・行動に必要な情報を残す

文書には、読者の今日の判断・行動を変える記述だけを置く。コードを読めば分かることの書き写しや、もう無い物の説明を足さない。コードが変わっても文書は置いていかれ、実態とずれた前提で読み手を動かしてしまうから。

足したり変えたりした記述は、コード・設定・ほかの文書の実態と同じことを言うようにする。食い違った文書は、無いより悪く、読み手を誤った前提で動かすから。

## 前提と用語を明確にする

前提はぼかさず言い切る。「環境に依存するので例示に留める」ではなく、「デフォルトは X、同等の機能があれば Y も可」のように、既定値と代替を認める条件を示す。読み手が同じ判断を再現できるようにするためである。未確認の前提を事実として断定せず、何が未確認かを示す。

専門用語は、指したい概念を正確に表す語を選び、開発の現場で定着している呼び名をそのまま使う。どの呼び名にするかは、開発者が同僚に Slack で書く語かで判断する。多くは原語かカタカナ語で、例えば「ツール」「ワークスペース」「flaky なテスト」はそのまま書く。「認証」のように漢語で定着している用語は、その漢語を使う。意味の近い別の用語や、「仕組み」「処理」「もの」のような意味の広い語で済ませず、和語にも言い換えない。用語を取り違えると読み手は別の概念として読み、意味の広い語では何を指すのかを特定できず、言い換えた語は読み手が検索や会話で使う語とずれて同じものを指しているのか分からなくなるから。

近い概念は呼び分ける。例えば、Issue を立ててから閉じるまでの時間はリードタイム、エージェントが作業している時間は作業時間と呼び、どちらも単に「時間」とは書かない。定着した用語でも読み手が知らなそうなものには、初めて出たところで短い説明を添える。

会話の中で作った呼び名・略称・比喩を、会話の外の人が読む文書・画面・Issue に出すときは、初めて出たところに定義を添える。例えば「切替窓」を使うなら「切替窓（新環境へ接続先を切り替える時間帯）」と説明する。書き手が共有している前提を、読み手も知っているとは限らないから。

数値・条件・例外・否定を、資料に無いのに足したり、書き直しで落としたりしない。書き直しで事実や条件が変わると、同じ文書を読んでも違う判断になるから。

## 作業の状態と決定の経緯を分ける

開発の計画・進捗・未解決の作業は Issue で管理し、リポジトリの文書には書かない。Issue と文書で作業の状態を二重に持つと、片方が更新されず、次に行う作業を誤るから。関係者への進捗報告は Issue を参照し、別の管理先にしない。文書の区分は [document-types.md](document-types.md) で確認する。

決定の経緯は文書に溜めず、理由はコミットや PR に残す。ADR（Architecture Decision Record、設計上の決定記録）を独立した保存先として設けない。「決着済み」「再検討しない」などの履歴が残ると、状況が変わっても前提として読まれ、次の判断を縛るから。

現在有効な選択と、それを理解・適用するための理由は文書に残す。設計案を判断するための代替案の比較も必要である。例えば「注文とキーを同じトランザクションで保存するため同じ DB を使う」は設計に残し、過去の会議で誰が別案を退けたかは残さない。調査結果・障害記録など、後の判断に使う事実の記録は残す。
