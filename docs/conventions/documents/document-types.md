# IT現場の文書分類

出典: [iwasa-kosui/tanteki](https://github.com/iwasa-kosui/tanteki) bcf2b1dのreferences/document-types.md（MIT、[NOTICE](NOTICE.md)）。

エンジニアやプロダクトマネージャーが文書の役割を選ぶための、この規約の分類である。全国共通の規格ではない。文書名は組織ごとに異なるため、読者・目的・残すべき情報で分類する。

## 区分

文書を次の3区分に分ける。

| 区分                     | 役割                                         |
| ------------------------ | -------------------------------------------- |
| stock（参照用の文書）    | 現状や仕様、設計、要求、判断を後から確認する |
| flow（作業を進める文書） | 計画や作業、進捗、進行中の運用を調整する     |
| record（事実を残す文書） | 調査結果、検証結果、障害の経過などを記録する |

`stock` には契約などの基準情報も含む。PRD、Design Doc、RFC はこの区分に置き、更新中やレビュー中でも区分を変えない。

この分類は情報の役割を表し、リポジトリに置くファイルの種類を推奨するものではない。`flow` には Issue 本文や関係者向けの進捗報告も含む。開発の計画・進捗の管理先と、決定の経緯の残し方は [accuracy.md](accuracy.md#作業の状態と決定の経緯を分ける) に従う。

`flow` に書かれた情報のうち、作業の完了や変更後も正式な参照先として残す必要がある現行の仕様・設計は `stock`、調査・検証の事実は `record` に移す。`record` は作業の進捗管理には使わない。

## 役割を決める

資料を確認し、本文を書く前に次を決める。これは作業用メモであり、成果物にそのまま載せる必要はない。

- 種類と区分: 何の文書を書くか。`stock`、`flow`、`record` のどれに当たるか。
- 読者: 誰が読むか。何を知っているか。
- 目的: 読後に何を判断・実行できるか。
- 対象外: この文書では何を管理しないか。
- 根拠: どの資料を参照するか。何がまだ分からないか。

質問するのは、作成を左右する重大な情報が足りない場合に限る。未確認の数値、承認、仕様は補わず、確認待ちでも書ける部分は進める。組織の文書名が以下の分類になければ、この5点で役割を定める。

`stock` には作業の進捗、PR番号、Jira課題IDを入れない。Issue から仕様・設計の文書を参照する。仕様が定める業務上の状態や、RFC の提案・採用などの状態は残す。`flow` と `record` に必要な日付、担当、時系列、課題への参照を機械的に削除しない。

種類別の資料は、文書の役割と、その役割を果たすために説明すべき内容を定める。たとえばDesign Docでは、実現方法に加え、背景・目的・スコープ・制約に照らしてその方式を選ぶ理由を説明する。必要な語句が揃っていても、内容の関係を読者が理解できなければ役割を果たしていない。

具体的な見出し、順序、節の数は、原資料と読者に合わせて[文書全体の構成](structure.md#文書全体の構成を決める)で決める。種類別の説明をそのまま章立てに置き換えない。必要な根拠が資料にない場合は、未確認事項として扱う。

## カテゴリから参照先を引く

書く文書に合うカテゴリを選び、そのファイルだけを読む。7ファイルをすべて読む必要はない。

- [戦略・プロダクト](types/strategy.md): ビジョン・戦略、製品企画の概要（Product Brief）、製品要求書（PRD）、ロードマップ。
- [調査・分析](types/research.md): 問題定義、顧客調査、分析結果、実験計画、環境調査。
- [要求・仕様](types/requirements.md): 要求仕様、ユーザーストーリー、ユースケース、機能仕様、非機能要求、API仕様。
- [設計・意思決定](types/design.md): 設計書（Design Doc）、技術提案（RFC）、脅威モデル、データモデル設計。
- [QA・リリース](types/qa-release.md): テスト計画、テスト結果、受け入れテスト手順書、リリース計画、データ移行計画。
- [運用・障害](types/operations.md): 運用手順書（Runbook）、サービスの品質指標・目標（SLI/SLO）の方針、インシデント記録、障害の振り返り、廃止告知。
- [知識・計画・記録](types/knowledge.md): プロジェクト計画、進捗報告、会議メモ、確認依頼、README、ガイド、FAQ。

## 参考資料

次は、文書の役割を考える際に参照した一次資料である。ここで定めた3区分の外部規格ではない。

- [Google Documentation Best Practices](https://google.github.io/styleguide/docguide/best_practices.html): Design DocとPRDを実装案への意見収集に使い、実装後は判断の記録として残す指針。
- [RFC 2026: The Internet Standards Process](https://www.rfc-editor.org/rfc/rfc2026): RFC、Internet-Draft、標準化の段階、文書の正式な状態を区別する資料。
